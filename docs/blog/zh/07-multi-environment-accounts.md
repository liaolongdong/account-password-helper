同一套后台系统，我有四套账号：dev、test、staging、prod。域名分别是 `admin-dev.example.com`、`admin-test.example.com`、`admin-staging.example.com`、`admin.example.com`。看起来很好区分，但真正登录时，问题往往不是「记不住密码」，而是**密码管理器把哪个账号递给了你**。

填错环境的后果可大可小：轻则登录失败，重则用测试账号改掉生产数据。这篇文章从匹配规则、账号命名、自动保存和团队协作四层，给出一套可以落地的做法。

## 为什么「填错环境」不是小概率

大多数密码管理器按「站点」匹配：主域相同就算同一个站。对普通用户这是合理简化，对开发者却是风险来源：

- `dev.example.com` 与 `example.com` 可能被视作同一站；
- 同一主域下的多个后台共用登录页，列表里出现一长串相似账号；
- 自动填充默认选中最近使用或排序靠前的条目，未必是当前环境；
- 自动提交开启后，错误账号可能直接把登录请求发出去。

所以，多环境管理的核心不是「记住更多密码」，而是**让匹配规则、账号命名和操作动作共同降低误填概率**。

## 第一层：让匹配规则替你挡住

最有效的一层是域名匹配。可以把它拆成三档，按需使用：

1. **精确主机名（默认）**：只有规范化后的 host 完全一致才展示。`admin-dev.example.com` 的条目不会出现在 `admin.example.com` 上，这是多环境隔离的底线。
2. **精确 + 通配条目**：允许把网址写成 `*.example.com` 的条目在整站子域出现。适合「一套测试账号本来就服务整个子域家族」的情况，由你逐条决定哪些条目可以放宽。
3. **同主域名兜底**：当前域名没有账号时，才带出主域与兄弟子域的条目，并明确标注「跨子域」。这是兜底，不是默认。

`localhost` 和 `127.0.0.1` 要单独处理：本地项目经常用不同端口并行，`localhost:3000` 与 `localhost:5173` 应该按端口隔离；页面没写端口时再放行全部本地条目，方便联调。

账号密码管理助手把这些规则做成了管理页头部的三档开关，并在每条跨子域结果上给出徽标。具体实现与踩坑可以看[跨子域名匹配三档的实现](https://liaolongdong.github.io/account-password-helper/blog/05-cross-subdomain-matching.html)。

## 第二层：把环境写进账号命名和标签

匹配规则解决「哪些账号出现」，命名和标签解决「出现之后一眼选对」：

- 用户名尽量带环境标识，例如 `qa+staging@example.com`、`deploy-prod@example.com`；
- 标签按环境或用途固定，例如 `prod`、`staging`、`qa`、`ci`，不要临时起名；
- 收藏只留给每天都要用的账号，避免收藏区被多环境账号塞满；
- 备注写清楚这个账号能做什么、不能做什么，例如「只读」「可发布」「仅测试」。

标签和命名不是装饰，它们是你在一长串相似条目里做快速判断的依据。

## 第三层：把自动提交当成危险动作

自动填充和自动提交是两件事。填充只是把值写进输入框，自动提交则会把登录请求发出去。

建议：

- **生产环境默认关闭自动提交**，需要时再手动点登录；
- 测试环境可以开启自动提交，用快捷键完成高频回归；
- 对涉及资金、权限变更或不可逆操作的后台，即使开启了自动提交，也要在提交前确认当前环境；
- 把「填充并登录」当成显式动作，而不是页面加载后的默认行为。

这不是工具能力问题，而是操作边界问题：越接近生产，越应该让最后一个动作由人确认。

## 第四层：保存与覆盖要可预期

多环境场景下，自动保存也很容易制造混乱：

- 同一域名、同一用户名但密码变化时，工具应提示「更新」而不是静默覆盖；
- 不同用户名应新增条目，不能因为网址相同就合并；
- 保存判重口径不应随匹配档位改变。放宽展示范围是为了方便查找，不代表保存时可以把不同环境的账号视为同一条；
- 定期检查重复条目，但不要用「一键去重」误删不同环境的账号。

账号密码管理助手把自动保存的判重口径与展示匹配分开：放宽档位只改变「哪些账号可见/可填充」，不会改变保存时对「同域名 + 同用户名」的判断。

## 团队协作：工具可以分享，凭据不要群发

多环境账号经常需要团队协作，但**不要把密码发在群聊、文档或截图里**。更稳妥的做法：

- 每个人使用自己的账号，按角色授权，避免共享同一个生产账号；
- 必须共享的凭据，使用团队密码管理器或企业密钥管理工具，并开启审计；
- 本地优先工具适合个人管理；它不提供团队同步，也不应该被当作团队共享盘；
- 交接时转移的是「账号归属与权限」，不是一条聊天记录里的明文密码。

如果你只是想推荐工具给同事，可以分享产品说明页，而不是分享你自己的库。

## 上线前检查表

- [ ] 匹配档位是否符合当前项目：默认精确，确需放宽时逐条确认；
- [ ] `localhost` / `127.0.0.1` 是否按端口隔离；
- [ ] 生产环境是否关闭了自动提交；
- [ ] 账号命名和标签是否能一眼区分环境；
- [ ] 自动保存的更新/新增提示是否被正确确认；
- [ ] 团队共享是否走了合规渠道，而不是群聊；
- [ ] 最近一次加密备份是否可用。

多环境管理的目标不是「永不填错」这句口号，而是让每一次填充都发生在可解释的规则里：**为什么这个账号会出现、为什么这个环境不会串号、为什么最后一个提交动作由你确认**。
