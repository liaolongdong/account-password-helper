## 一、策略定位（所有操作前的第一步）

### 1.1 为什么先改定位

官网与插件当前的免责声明：

> “本插件的所有数据均保存在本地（敏感信息加密保存），仅用于开发、测试和普通生产环境登录使用，严禁保存办公或个人敏感密码（如银行、支付、社交核心密码），如发生密码泄露，后果自负！”

这段话带来三个负面影响：

1. **信任劝退**：用户搜索“密码管理器”，看到一个密码管理器说“别存重要密码”，第一反应是不信任，直接划走。
2. **拉低 Featured 评价**：Chrome 团队人工审核时会评估“用户价值”，这条声明让插件显得定位模糊、缺乏自信。
3. **口碑传播吃亏**：推荐者很难用一句话向别人说清“它是给谁用的”。

但插件的功能组合里有一个非常稀缺的差异化卖点：**精确域名匹配区分多测试环境、自动勾选协议、免点登录、自动保存凭证**——这几乎是**为开发者/测试人员管理多环境测试账号量身定做的**。

### 1.2 两个定位方案

| 维度       | 方案 A（主推）：开发者/测试人员工具              | 方案 B（辅助）：隐私优先密码管理器                |
| ---------- | ------------------------------------------------ | ------------------------------------------------- |
| 一句话定位 | 开发者和测试人员的多环境账号管理神器             | 零云端、纯本地、免费的隐私密码管理器              |
| 目标用户   | 程序员、QA、运维                                 | 隐私敏感的普通用户                                |
| 竞争格局   | 几乎无直接竞品，蓝海                             | Bitwarden/1Password 强势，但“纯本地+免注册”有差异 |
| 功能契合度 | 精确域名匹配、自动勾选协议、多环境账号，直接命中 | AES-256-GCM、密码数据不上传，直接命中             |
| 推广渠道   | V2EX、掘金、GitHub、CSDN                         | Reddit r/privacy、Product Hunt                    |
| 风险       | 用户群相对窄                                     | 易被拿去与成熟商业产品功能对比                    |

**结论：以方案 A 为主定位，方案 B 作为安全背书副线。** 全部对外文案先讲“为开发者/测试人员而生”，再用“本地加密、密码数据不上传”支撑可信度。

**执行原则（品类词与定位语分工）**：标题与摘要保留「密码管理器 / Password Manager」品类词负责搜索流量（用户搜的是品类，不是人群）；定位语与详细描述首段承担「开发者/测试人员多环境账号管理」的差异化叙事。两者并行不冲突——搜索来的用户先被品类词命中，再被定位叙事转化。

### 1.3 安全声明改写文案

**原文（建议替换）**：

> 本插件的所有数据均保存在本地（敏感信息加密保存），仅用于开发、测试和普通生产环境登录使用，严禁保存办公或个人敏感密码（如银行、支付、社交核心密码），如发生密码泄露，后果自负！

**改写后（中文，推荐）**：

> 账号密码管理助手为开发、测试与日常登录场景而生：所有数据仅保存在浏览器本地，敏感字段以 AES-256-GCM 逐字段加密，密码数据永不经过网络传输——扩展唯一的出站行为是每 6 小时一次的版本更新检查（匿名读取 Chrome 商店可达性与 GitHub Releases 版本号，不携带任何账号数据）。为保障您的资产安全，建议不要在任何浏览器扩展中存放银行、支付等高敏感凭证。

**改写后（英文）**：

> Account Password Helper is built for development, testing and everyday sign-in scenarios. All data stays in your browser and sensitive fields are encrypted one by one with AES-256-GCM; your passwords are never transmitted over the network — the only outbound request the extension makes is an anonymous version check every 6 hours (Chrome Web Store reachability, then the GitHub Releases API for the latest version number), which carries no account data. For the safety of your assets, we recommend not storing highly sensitive credentials (banking, payment, etc.) in any browser extension.

**改动逻辑**：把“严禁……后果自负”换成“为……而生 + 建议不要存放”，保留合规提醒，同时把免责声明变成了正向的目标场景描述。第二处改动更关键：扩展并非「零网络」——`utils/updateChecker.ts` 每 6 小时会匿名探测商店可达性、不可达时回退 GitHub Releases API，因此统一口径为「密码数据不上传 + 主动披露唯一一次匿名版本检查」，与 `README.md`、`privacy.html` 和 `_locales` 保持一致（绝对化表述属于可被投诉的虚假隐私承诺）。

### 1.4 一句话定位语（多场景复用）

- **中文**：账号密码管理助手——为开发者和测试人员打造的本地加密多环境账号管理神器，快捷键一键登录，密码数据不上传。
- **英文**：Account Password Helper — a local-first, encrypted credential manager for developers & QA. One-keystroke login, no password uploads.

### 2.3 / 2.4 详细描述（中英，见 CWS_FILL_CONTENT.md）

中英两版完整正文以 `CWS_FILL_CONTENT.md`「第二步 → 说明」为准，其结构是按 Chrome 商店的元数据要求写的，改稿时保持这四条不变：

1. **一个卖点只在一个小节展开**：被判定堆砌的是「同一句话在为什么选它 / 适合谁 / 安全架构 / 功能全览 / 常见问题里各抄一遍」，不是小节数量或篇幅。修法是把每个卖点指定到唯一归属小节，**小节结构本身保留**——上限 16,000 字符，砍掉整节只会白白丢掉长尾词面。⚠️ 去重只删**重复的那半句**：卖点的能力规格归【功能全览】，人群条目里保留自己的动机与用词（【适合谁】的「从其他密码管理器换过来」就是这样），不要把整句删到只剩骨架——2026-09-10 三次修订就犯过这一次，被评审问回来后回填。同一个卖点还可以**按"机制 vs 价值"拆到两节**：TOTP 的扫码 / RFC 6238 / 活码机制归【功能全览】，"不必摸手机、不必切验证器"的价值句归【为什么选择它】——这是四次修订（2026-09-10）被评审追问「TOTP 为什么不保留」后确立的写法：**卖点必须可见，重复才要消除**；被点名的功能先回到它该在的小节，再回头删另一节里重复的那半句。同理，「真的完全免费吗 / 能从其他密码管理器导入吗」这类问答即使与正文有概念重叠也要保留，只把答案限制在本节独有的那部分事实（付费事实 / 操作路径）。

3. **实现细节按读者分层，不是一刀切删除**：随机 IV、Base64 密文格式、RFC 6238、Web Crypto、Diceware、词库条数、SLA 毫秒数这些留在 README / ARCHITECTURE / 官网 / llms.txt；用户可自行核对的加密事实留在商店说明——**AES-256-GCM 写进摘要与【安全架构】，PBKDF2 迭代次数只写在【安全架构】**（审核员的「单一事实来源」要求是指一个卖点只讲一次，不是禁止披露技术事实）。

5. 规划下月版本功能点与 1-2 个内容选题。
6. 检查 Featured 徽章状态；若获批，截图数据增长曲线用于对外宣传。
