## 一、结论先行

1. **这不是"数据量大"的问题，是"600 行全部进 DOM + 任意一次交互重排整张表"的问题。**
   实测口径下，600 条的过滤+排序计算成本在 **1～5 毫秒**量级，而 600 行常驻 DOM 的重建成本在
   **700 毫秒**量级、整表样式失效在 **85 毫秒**量级——两个数量级的差距。任何只让"算得更快"的方案
   天花板不到 5 毫秒。

2. **分页能拿到收益，但只拿得到其中一份，且要付交互回归的代价。**
   分页的有效机制只有一个：减少常驻 DOM 的行数。同一个机制，虚拟滚动也能做到；而下面第五节列出的
   5 个缺陷，分页一个都治不到——它们按"渲染行数"结算，不按"数据条数"结算，页大小 50 就变成
   50 行整表重渲染。
   曾被列为第三选项的"窗口化渐进渲染"（模拟无限滚动）已在真机被判否决，因为它在 `el-table` 上
   每放开一帧就要重排已渲染的全部行，总成本反而上升（见本条原推荐路线的结算：9.8）。
   〔2026-09-23 更新：这条判断仍然成立——分页**只**买到"一次进 DOM 的行数"这一份收益，
   第五节那 5 个缺陷是由 P1/轮四分别修掉的，不是分页修的。分页已于当日落地，交互回归的处理见 9.11。〕

3. **仓库里已经有验证过的正确答案——但只在侧边栏那种 `v-for` + `v-memo` 列表上成立。**
   侧边栏用 `v-memo` + 首帧 30 行 + rAF 批量 60 行续渲染
   （`components/sidepanel/SidepanelAuthView.vue:204-262`）解决了同一问题，并已在"秒开 SLA"下验证。
   管理页当时判断"缺的正是这一套"，**这条判断已在 9.8 被真机推翻**：`el-table` 每次 `data` 换引用
   都重排已渲染的全部行，分帧放开等于把整表重排重复 15 遍，总时长 19.9 s → 39.4 s。

4. **推荐路线：先止血（消除 5 个整表重渲染缺陷，零交互变化），再把渲染窗口化，最后才考虑数据层改造。**
   分期见第七节。〔2026-09-23 更新：第一档已完成；第二档已实测否决（9.8），因此剩下的路只有
   "减少每行组件实例"或"减少一次 flush 里的行数（分页 / 虚拟滚动）"。后一条会改变可感知交互，需先拍板；
   前一条**已落地**（轮四，9.10）：先定价出"完全去掉操作列 tooltip"的上限（9.9，wall −40%，DOM 逐字一致），
   再用"全表共享一个 `virtual-triggering` 实例"把它取回来，实测 600 行首屏整表挂载 wall 约**腰斩**，
   且悬停延迟、隐藏时序、移入浮层保持显示、`aria-describedby` 逐条与改前等价（真机 10 例）。
   第三档"减少一次 flush 里的行数"**同日已拍板为分页并落地**（9.11）：管理页每页 50/100/200、默认 100，
   2000 条上限下一次进 DOM 的行数从"全部命中"变成恒为一页，同口径实测 2000 条的整表挂载
   180.2 s → 3.0～5.4 s，且与 600 条档位不可区分（成本对总条数的依赖被切断）。〕

5. 顺带：issue #89 里的第二个诉求（`qq.com` 与 `mail.qq.com` 通用）在本分支已实现为
   "跨子域匹配三档"（`utils/domain.ts:405-407` `resolveMatchTier` + 档位设置弹窗 + 侧边栏全站检索范围），
   可直接回复该用户，不必另做。

6. **落地进展（2026-09-22）**：P1 已按上述路线完成，同一时间窗内的真机对比是
   `addClick` 阻塞 -60%、`save` 的渲染进程脚本时长 6.419 s → 0.221 s、`favorite` 阻塞 -46%，
   而 600 行首屏不变（那是 P2 的范围，P2 后据实测否决，见 9.8）；悬浮路径两侧仍同量级，原因与"为什么这次不动它"见 9.3。
   改动清单、两处口径变化与全部数据在**第九节**。

## 二、先把事实校准

用户 2026-09-21 的追问回复里有两条决定性事实：

- 「600 条数据不是在单个页面上，是在**管理页面**上，单个页面不会出现这么多的」
  → 问题面是 `entrypoints/options/`，不是侧边栏。侧边栏因按当前域名预筛（`utils/passwordFilter.ts:79-87`），
  通常只有几条到几十条，这与"用户没抱怨侧边栏卡"一致。
- 「打标签因为页面太过卡顿就没有使用这个功能」
  → 标签相关路径是被感知最重的入口之一，见第五节缺陷 1、缺陷 4。

因此本评估的主战场是**管理页渲染层与交互层**，数据层是次要矛盾。

## 三、实测证据

### 3.1 计算层不是瓶颈（实测）

命令：`pnpm exec vitest bench benchmarks/sidepanel-p0.bench.ts --run`（本机 2026-09-22）

> **口径：这张表是"拼音匹配器未就绪"态下量到的。** 该文件从不调 `warmPinyinMatcher()`，拼音成本用例
> 住在 `benchmarks/pinyin-keyword.bench.ts`（自带预热、独立 worker，理由写在它的文件头）。一个 bench
> 文件跑在同一 worker、预热又在收集阶段完成，所以两者混在一个文件里会让 `all scope + keyword match`
> 变成"每个字段多问一遍拼音"，数字上浮且与下表不可比。复跑对比前先确认跑的是哪个文件。

| 场景（全库、无关键词优先）                     | 500 条  | 2000 条                  |
| ---------------------------------------------- | ------- | ------------------------ |
| 过滤 + 排序（生产实现 `sortPasswordEntries`）  | 1.23 ms | 4.83 ms                  |
| 域优先级排序（同上）                           | 1.20 ms | 4.95 ms                  |
| 行标签呈现：已缓存记录 vs 每次重算 parse+style | —       | 0.08 vs 2.01 ms（23.1×） |

两点含义：

- 600 条的 JS 计算成本个位数毫秒。**分页若只为"少算一点"，收益上限就是几毫秒。**
- 同一份 bench 已经量化出一个现成的免费午餐：行标签呈现缓存化 **23 倍**。它已在侧边栏落地
  （`PasswordListItem.vue:88` 用 `buildTagPresentationRecords`），而管理页每次渲染仍逐次重算
  （`PasswordTable.vue:126`），且同一行把 `parseTags(row.tag)` 调了两遍（`:115` 与 `:117`）。

### 3.2 加密与存储层：没有隐藏的全量重加密（源码级）

最初我假设"保存一条会重加密整库"，**复核后不成立**，记录在此以免有人重复踩：

- PBKDF2 迭代 600,000 次（`utils/encryption.ts:131`），但只在 `createSession`
  （`utils/sessionManager-storage.ts:593`）走；CRUD 取三级缓存的数据密钥
  （内存 → `storage.session` → AES-GCM 解包，`sessionManager-storage.ts:287-359`），**不在 PBKDF2 路径上**。
  单次派生实测 1.6～2.5 秒（`tests/utils/encryption.test.ts` 口径），若它在保存路径上会立刻暴露。
- 密文是**按条目、按字段**（`passwordCrud.ts:23` 五个敏感字段），保存 1 条只加密这 1 条的非空字段
  （`:91`），其余 599 条密文原样搬运。
- 真实成本是：整个集合存在单键 `account_passwords` 下（`storageKeys.ts:8`），每次写都要序列化并重写
  整包 600 条（`passwordCrud.ts:105-107`，估 180～240 KB，为算术推算未实测），叠加 Windows 杀软扫描
  （`agents.md`「Storage」章节已记录该已知问题）。
- 一次保存的跨入口级联值得记账：SW 侧 `onChanged` 未命中 metadata 标记时会
  `invalidatePasswordCache()` + `warmPasswordCache()`，即 **3000 次 AES-GCM 解密 + 600 条明文 JSON 序列化 +
  整包再加密写 `storage.session`**（`backgroundServices.ts:672-694` → `passwordCache.ts:202-245,420-440`）。
  它跑在 SW 进程，不直接阻塞管理页主线程，但在 Windows 低端机上与渲染进程抢 CPU 与磁盘。

### 3.3 渲染层是瓶颈（实测，复刻探针）

探针：`benchmarks/large-vault-dom-probe.html`（本次新增）。它按 `PasswordTable.vue` 的真实结构复刻
每行 10 列、约 62 节点、5 个操作按钮、最多 3 个标签、TOTP svg、固定左右列 sticky、以及
`transition: all .3s` + `:hover{transform;box-shadow}`（`PasswordTable.vue:393-400`）。
在真实浏览器中分别以 30/60/100/200/600/2000 行测量主线程同步阻塞时长（取 3 次中位数）。

| 渲染行数 | DOM 节点 | 全量重建  | 整表样式失效 | 模态框锁滚强制布局 |
| -------- | -------- | --------- | ------------ | ------------------ |
| 30       | 1 904    | 26.6 ms   | 1.5 ms       | 0.3 ms             |
| 60       | 3 777    | 53.5 ms   | 2.9 ms       | 0.4 ms             |
| 100      | 6 283    | 118.3 ms  | 10.2 ms      | 1.5 ms             |
| 200      | 12 534   | 207.9 ms  | 10.1 ms      | 1.0 ms             |
| 600      | 37 545   | 705.6 ms  | 85.1 ms      | 5.0 ms             |
| 2000     | 125 094  | 2930.3 ms | 107.9 ms     | 9.4 ms             |

三条可读结论：

- **成本 ∝ 渲染行数，近线性**，常数很大（重建约 1.2 ms/行，整表样式失效约 0.14 ms/行）。
  真实 el-table 因每行 5 个 tooltip 包装组件 + checkbox + icon 组件，节点数比复刻更高
  （静态估 75～90 节点/行、45～55 组件实例/行）。
- **一个被实测推翻的假设**：模态框打开时 `useLockscreen` 改 body 宽度 + 读 `scrollHeight` 引发的强制布局
  只有 5 ms（600 行），**不是"点新增卡"的主因**。真正的主因排序应为：
  ① 点击后先串行等两次 `chrome.tabs.query`（`entrypoints/options/App.vue:714` 与 `:717`——用户点的是扩展
  自己的页面，所以一定走 fallback 分支去查全部标签页再排序）；
  ② 对话框子树首次挂载（含 T 个标签 `el-option` 与 428 行的密码生成器 popover，且 `el-select`/`el-popover`
  的 `persistent` 默认 true → 首挂后常驻）；
  ③ 整表规模带来的重排与绘制底子。
- **`content-visibility` 不是免费捷径**：给 `tr` 加 `content-visibility:auto` 后 600 行挂载从 628 ms
  变成 1087 ms（table-row 不支持布局包含），此路排除。

## 五、分页治不到的 5 个点

以下每一项的成本都按"渲染行数"结算。分页只把 600 变成 50，不消灭机制本身。

1. **悬浮任一标签 → 整张表重渲染。** `useTagOverflow()` 在 `PasswordTable.vue:319` 只调用一次，
   `overflowedTag` 是**整表共享**的响应式 ref：写入发生在标签 `@mouseenter`（`:129` →
   `useTagOverflow.ts:26`），读取发生在单元格模板里（`:122`），于是它被 `ElTableBody` 的渲染 effect 收集为依赖。
   鼠标每换一次标签值就变一次 → 整表重渲染（复刻口径 85 ms 起步，再叠加 Vue patch）。
   修复方向：溢出判定降为行内局部状态，或用纯 CSS 达成"仅截断时才提示"。

2. **每行 5 个 `el-tooltip` + 函数式 ref 写进响应式数组。** `:197-268` 每行建 5 个 tooltip，
   `collectTooltipRef` 每次渲染往 `tooltipRefs`（响应式 `ref([])`，`:333`）push，
   `closeAllTooltips()` 在 `onBeforeUpdate`（`:354-357`）里全量遍历 `onClose()`。
   而 `onBeforeUpdate` 注册在 `PasswordTable` 自身、行内容却由子组件 `ElTableBody` 渲染——
   整表重渲染时函数式 ref 会再 push 一轮，但清空不一定跟着发生，引用集合存在只增不减的风险
   （**未验证**，需 P0 真机确认；机制层面的 3000 个 tooltip 实例与每次渲染 3000 次 ref 回调是确定的）。

   > 落地状态见 9.4：「只增不减」未被坐实（旧实现每次 `onBeforeUpdate` 会清空），已确认的是响应式写入开销。
   > P1 只把容器换成非响应式 `Map`（见 9.1 第 2 行）；**逐行 5 个 tooltip 实例本身留到轮四才消掉**，见 9.10。

3. **每次击键重排全部高亮，而不是全部过滤。** `App.vue:97` 传给表格的是**未防抖**的 `searchKeyword`，
   防抖只作用于过滤（`usePasswordManagement.ts:136-141`）。于是每敲一个字，约"行数 × 每行文本单元格"个
   `SearchHighlight` 全部重算；子串未命中时每个单元格还要各跑一次 pinyin-match DP
   （`utils/searchMatch.ts:92-104`）。

4. **标签候选集 `availableTags` 与 `el-select` 的 O(T²)。** `usePasswordManagement.ts:185` 每次
   `passwords` 变化就 O(N×标签) 聚合一次；结果进三处 `el-select`（`SearchFilterBar.vue:49`、
   `PasswordFormDialog.vue:106`、`BatchTagDialog.vue:38`），EP 内部 `optionsArray` 对 `optionValues`
   做 `findIndex` 是 O(T²)，且 `el-select` 的 `persistent` 默认 true → 弹窗关闭后 T 个 option 仍常驻、
   仍会随候选集变化重算。**分页不改变 T，"点新增"这一次一分不省。**

5. **保存/收藏/删除后可能整表重建。** 设计意图是"就地更新 + 跳过 watcher"（`usePasswordManagement.ts:477-479`），
   靠 `runLocalOperation` 的 `setTimeout(0)` 清除标志（`useLocalOperationGuard.ts:33-44`）来抑制
   `useStorageWatcher.ts:62-72` 的 `loadPasswords()`。但 `chrome.storage.onChanged` 经 IPC 派发通常**晚于**
   这个宏任务，守卫大概率已经失效 → 一次保存变成 3000 次解密 + 数组换引用 + 整表重排 + 平滑滚动
   （`scrollToPassword`，`:407-422`）。**未验证，属 P0 必测项**；但无论真假它都不是分页能解决的。
   > 落地状态见 9.4：真机已坐实（`save` 场景渲染进程脚本时长 6.419 s → 0.221 s），已改为事件驱动解除。

顺带记录两个与卡顿同源、但属正确性侧的问题（不构成本次交付范围，仅登记）：
`batchExportSelected`（`:697-698`）与 `batchEditTags`（`:759`）用 `includes`/`find` 在选中集上做 O(N·M) 查找；
`deletePassword` 的动画收尾直接对 `el-table` 的 tbody 做 `row.remove()` / `insertBefore`（`:568-577`）。

## 六、分页会引入的交互回归（~~需先拍板才做~~ 已拍板，落地解法见 9.11）

`agents.md` 要求不得未经确认改变既有交互。分页必须同时定义清楚：

- 跨页批量选择：`selectedIds` 目前隐含"选中项都可见"，`batchDelete` / `batchEditTags` 读的是全集
  `passwords.value`。分页后会出现"看不见的选中项"，要么保留跨页选中并新增"已选 X 条（跨页）"提示，
  要么切页即清空——后者会让批量编辑标签这个主力功能退化。
- 删除动画与 `detachRow` 的 DOM 手术（`:568-577`）与页码切换叠加时的复原位置。
- "总计 N 条 / 筛选后 M 条"（`App.vue:64-81`）与页码控件的信息重复。
- 切页是纯内存切片还是走存储读——若走存储读，Windows 慢磁盘下每次翻页都是一次整包 IO。

> **落地状态（2026-09-23 下午，见 9.11）**：四条都有确定答案。① 跨页选中**保留**并显式报差额
> （`row-key="id"` + `reserve-selection`，分页条写「已选 X 条，其中 Y 条不在当前页」，批量操作作用全集）；
> ② 删除动画只在**当前页有该行 DOM** 时发生（`findPasswordRow` 命中才淡出、摘除、失败插回），
> 跨页批量删除时不在本页的选中项跳过动画直接随同一次 `deletePasswords` 落盘，`insertBefore` 的参照节点恒在同一 tbody 内；
> ③ 页码控件与「总计 / 筛选后」读数是两套信息、不做重复展示，页码条只补「第 X / Y 页」；
> ④ 翻页是纯内存切片（`source.value.slice`），零存储读、零解密，实测一次翻页渲染进程脚本 36～46 毫秒。
> 另外两处本次落地时才暴露、原清单没列的交互点：保存后定位需要**先换页再滚动**（`revealIndex`），
> 以及换每页条数时不能拿旧档位的总页数钳位（`pageForSizeChange`）。

## 八、P0 基线落地记录（2026-09-22）

第七节 P0 的验收前置已经建好，实际形态与计划有一处偏差：没有复用 `e2e/harness.ts`。
它是 `@playwright/test` 的夹具（`base.extend` 出 `extContext` / `optionsPage`），在裸 node 脚本里
没法直接消费；并且它取扩展 ID 走 `waitForEvent('serviceworker')`（30 s 超时），实测这一等在无头模式下
时灵时不灵。因此单独写了 `benchmarks/measure-options-perf.mjs`：ID 按加载路径算
（`--load-extension` 的 ID 是绝对路径 sha256 前 32 位 hex、`0-f` 映射到 `a-p`，纯函数不会失败），
驱动 e2e 同款 Chrome for Testing 加载 `pnpm build` 的真实产物 `.output/chrome-mv3`，
在真实 `options.html` 上按场景测量——jsdom 量不出布局，复刻探针只能证明机制，两者都无法证明"改的是真代码"。

- **夹具**：合成条目直接写 `chrome.storage.local`，走 `passwordCrud.ts` 的全明文直通分支，
  目的是把解密成本从测量里剥掉、只留渲染层；profile 用 `mkdtemp` 建临时目录、用完即删，
  不落任何真实凭据。
- **场景**：`mount` / `addClick` / `tagHover` / `rowHover` / `keystroke` / `favorite` / `save` / `scroll`。
- **每个场景同时产出四类信号**：`wall`（辅助，含 Node 往返）、longtask（条数与超出 50 ms 之和，
  按 `__from` 开窗，避免把上一场景延迟上报的任务算进来）、CDP `Performance` 计数器增量
  （Layout / RecalcStyle / Script / **Paint / Commit**——缺后两项会把"大表重绘"误读成"JS 慢"）、
  DOM churn 探针（区分就地 patch 与整棵子树重建）。可选 `--profile save,favorite` 另采 CPU profile。
- **`--fresh`**：每个样本重开页面。一次交互的工作常排在几秒后的独立任务里，静默判据只保证"当下不忙"，
  挡不住它污染下一个场景（同一份产物、同样的收藏点击，在不同前置状态下测出 36 s 与 22 s 阻塞）。
- **它是测量工具，不是门禁工具**：脚本只输出 `benchmarks/results/options-<label>-<rows>rows.json`
  和中位数汇总，不做任何阈值断言。第七节 P0 表里那几个数字是提评估时写的建议门禁，
  600 行真机的实际量级远宽于它们（见 9.5 与 9.8），因此没有把它们固化成 CI 断言——
  真要设门禁得先定"可接受的首屏"是多少，那属产品口径，需单独拍板。
- **`mount` 必须三个口径一起读**：`firstPaintMs`（第 15 行进 DOM）、`wallMs`（全量进 DOM）、
  `maxLongMs` 与阻塞之和。只报首屏会把 9.8 那次分帧读成 7.5 倍提速，只报总时长又会漏掉它确实改善了首屏——
  **换定义等于换结论**。

复现命令：

```bash
pnpm build
export E2E_EXECUTABLE_PATH="/tmp/cft/chrome-mac-x64/Google Chrome for Testing.app/Contents/MacOS/Google Chrome for Testing"
node benchmarks/measure-options-perf.mjs --rows 600 --repeat 5 --fresh --label before
# 改完代码重新 pnpm build 后，在同一台机器、同一时间窗内跑 after
```

四条已知限制，读任何一份 `benchmarks/results/*.json` 前都要先看：

1. **绝对值只在同一时间窗内可比**。本机曾出现测量期间负载从 4 抬到 16、从 10 爬到 54 的情况，
   跨窗口的差值不能当结论（9.5 与 9.8 都标注了当窗负载）。
2. **`mount` 不给 CDP 计数器**：导航会跨文档重置，计数器增量不可靠，因此该场景只有时长与长任务三类口径。
   缺键在汇总里结算成 `null` 而不是 `0`——写成 0 会被读成"实测为 0 秒"。
3. **`keystroke` 在 P1 的 before 侧连一次可用样本都没取到**（`press` 在 90 s 内不落地），
   该项改用 9.7 的同进程 A/B 代替，不构成真机前后对比。
4. **夹具是刻意全文明直通的**，所以"密文态下的真实首屏"仍未被实测（见十一节第 3 条），
   P3 启动前需要另建密文态夹具。

### 9.2 需要用户知道的两处口径变化

1. **高亮随防抖一起落地（200 ms）**：输入框本身仍是即时的（`v-model` 绑原始 `searchKeyword`），
   但行内命中高亮改为与过滤同一时刻更新。收益是每击键不再重排上千个文本单元格；代价是停手后高亮最长
   晚 200 ms 出现——同时修掉了旧实现"行已经筛过、高亮却还是旧词"的短暂不一致。
2. **守卫兜底上限 2 s**：守卫正常由本次写入对应的 `onChanged` 解除，2 s 只是没有事件时的兜底。
   两条相关事实需要记清：SidePanel 的收藏/填充写入经 `passwordCrud.ts` 的 1.5 s 防抖合并才落存储，
   因此那条路径上守卫实际会武装约 1.5 s（旧实现约一个宏任务就失效），上限取 2 s 正是为了盖住它；
   而"没有事件"的窗口只出现在**静默未落存储却返回成功**的路径（`updatePassword` id 未命中、
   `batchUpdatePasswordMetadata` 无字段变化、`moveToTrash` 空集）。
   代价口径：武装期间到达的**外部**窗口写入会被跳过一次刷新，并且这一次跳过本身就解除了守卫，
   因此后续事件恢复正常——恢复条件是"再来一次存储变更"，切回标签页不会补刷（`visibilitychange`
   只重跑认证检查）。最坏用户可见结果是列表少显示另一窗口的一条改动，存储侧无损失。
   旧实现的问题是反向的：守卫提前失效，于是每次本地保存都额外背一次整表全量重载。

### 9.3 评估后决定不做的两项

- **彻底消除缺陷 1 的共享 `overflowedTag` ref**：唯一不动交互的做法是把"一个标签"包成独立组件，
  让响应式读取从 `ElTableBody` 的渲染 effect 下沉到组件内部。代价是 600 行约 1051 个额外组件实例
  ——与本节"减少一次 flush 内被更新的组件数"的方向直接对冲，且 tooltip 的 `disabled` 只能经 prop 表达，
  改成命令式抑制会改变显隐时序。实测该场景（`tagHover`）前后差异落在噪声内，不足以支撑改结构。
  原计划"留待与 P2 一并处理（P2 之后每屏只有 30～90 行，多出的实例数才变得可接受）"——**该前提已随
  P2 一并否决（9.8）**，因此这一项现在只有在选定"减少每行组件实例"路线时才值得重提。
- **`el-select` 设 `:persistent="false"`**：会把"打开标签筛选下拉"从"读已挂载的 option"变成"每次重建"，
  属可感知的交互变化（下拉动画与焦点行为），按 `agents.md` 需单独确认。

### 9.4 两条"未验证"假设的结算

第五节缺陷 5 标着"未验证"，本次已用真机与单测双向坐实：

- 真机：`save` 场景 CDP `ScriptDuration` 中位数 **6.419 s → 0.221 s**（见 9.5），正是"一次保存变成
  全量重载"被消除的量级；`favorite` 的阻塞时长 **54.1 s → 29.0 s** 同理。
- 单测：[useStorageWatcher.localOperation.test.ts](../tests/composables/useStorageWatcher.localOperation.test.ts)
  以"事件晚于宏任务到达"为前置构造 7 个用例，其中迟到事件用例在旧实现下必红（旧口径 `setTimeout(0)`
  清除已在同一测试文件下复现失败）。

缺陷 2 的"**引用集合只增不减**"这一条**未被坐实，如实记录**：旧实现在 `onBeforeUpdate` 里会把数组清空，
因此在"整表确实重渲染"的路径上不会累积。真正成立的是另一半论证——每渲染一次要往**响应式**数组里
push 3000 个引用、并在每次 `onBeforeUpdate` 全量遍历 close。改法保留同样的关闭语义，只把容器换成
非响应式 `Map` 并让条目随 ref 卸载自行删除（顺带消除了"行未重渲染时旧实例被清空而残留"这一类边缘）。
收益量级因此远小于当初的估计，`favorite` / `save` 的数字改善应归因给缺陷 5 的修复而非这一条。

四点读法：

- **首屏不变（+3%，同一量级）是预期结果**：P1 治的是"每次交互额外重排整表"，600 行一次性进 DOM 的
  成本不在它的范围内（当时寄望由窗口化承担，该路线已在 9.8 被实测否决）。两侧 `probe` 完全一致，
  说明这不是"少渲染了"造成的假改善。
- **`save` 的脚本时长 6.419 s → 0.221 s（-97%）是缺陷 5 的直读证据**：保存后不再触发"全量重载 + 整表重排"
  这条被守卫漏掉的路径。`favorite` 与 `addClick` 的脚本/布局同向下降，是同一机制的其他出口。
- **`addClick` 阻塞 -60%、长任务 13 → 7**：对应缺陷 3/4（高亮同源、标签样式与 popper 对象身份稳定、
  两次 `tabs.query` 并发）。
- **本机测量窗口的环境噪声不可忽略**：这 55 分钟里整机负载从 10 爬到 54（同机另有会话在跑 jekyll 构建），
  因此绝对值只用于同窗口内的相对结论，跨窗口不可比。`scroll` 的 wall +69 ms 属此类噪声（阻塞 8 → 0）。

### 9.6 交互路径（悬浮 / 击键）——P1 的边界所在

这三个场景在同一时间窗内两侧各跑 3 次：

| 场景      | 侧     |       wall（ms）        |   阻塞（ms）    | 取样窗口                                       |
| --------- | ------ | :---------------------: | :-------------: | ---------------------------------------------- |
| tagHover  | before |     808 / 850 / 891     | 293 / 399 / 510 | 18:17–19:12、19:42、19:55 三次窗口             |
| tagHover  | after  |        742 / 965        |   388 / 1628    | 19:15、18:47 两次窗口                          |
| rowHover  | before |       813 / 1029        |    543 / 498    | 同上                                           |
| rowHover  | after  |       1094 / 822        |    496 / 445    | 同上                                           |
| keystroke | before |       无可用样本        |        —        | press 在 30 s / 90 s 超时内未落地（负载 100+） |

结论按"能证到哪一步写到哪一步"的口径给出：

- **悬浮路径两侧同一量级、区间互相重叠，P1 没有改善它，这与 9.3 的判断一致**：整表共享的
  `overflowedTag` ref 仍在，鼠标划过两个不同标签仍会让 `ElTableBody` 重渲染整张表。
  after 侧出现的 1628 ms 是取样窗口负载（load 20→54）造成的，与 before 侧同窗口的同类波动同量级。
- **击键路径未取得可比的真机样本**：before 侧三次尝试里 `press` 都在 30 s（后放宽到 90 s）内超时，
  即"上一次击键引发的重排还没结束，下一次输入落不进去"——这本身是缺陷 3 严重的旁证，
  但不能当作前后对比数据。该项以 9.7 的同进程 A/B + 结构论证代替。
- **本表所有绝对值都不对齐用户实际体验**：测量页面挂着 CDP `Performance`、longtask 与 MutationObserver
  三类观察器，且 `--fresh` 让每个样本重新承担一次 600 行首屏；这些开销都计在窗口内。
  可用于两侧同窗口比较，不可用于"用户会卡多少秒"的承诺。
- **归因补强（为何还剩一次整表 patch 没被消掉）**：两侧对 `save` 各采一份 CPU profile，
  Vue 的 flush 回调扫描（压缩名 `Ps`，其 self time 100% 由 `updateComponentPreRender` 调用）在两侧都仍是第一大项——
  before 占 59.0%（窗口 71.4 s，self 42.1 s）、after 占 50.2%（窗口 102.3 s，self 51.3 s）。
  两个单采样窗口的绝对值受负载影响不可比，但**构成没变**：P1 消掉的是"重复的整表 patch"，
  剩下那一次"600 行整表 patch"仍在。〔写这一段时的结论是"要由 P2 的窗口化拿掉"，该路线已被 9.8 否决，
  因此剩余出口只剩"减少一次 flush 里的行数"或"减少每行组件实例"两条，都需要先拍板。〕

### 9.8 P2 窗口化渐进渲染：真机否决（2026-09-23）

按 P1 的推荐路线把侧边栏那套"首帧只放开一屏、之后逐帧放开"搬进管理页表格
（`components/options/PasswordTable.vue` 的 `:data` 换成窗口化计算属性：首帧 20 行、每帧 +40 行，
`mousedown`/`keydown` 捕获阶段放开全量，保证表头全选与批量语义不变），实现与 9 例单测都通过，
**但真机 A/B 判它必须回退**。

测量口径：同一工作树的两次构建（只在 `:data` 绑定这一处不同，`PERF_HEAD` 未记录所以不给提交号）、
同一命令 `--rows 600 --repeat 5 --only mount`、同一时间窗（02:20–02:35）、
无头 Chrome for Testing 153（两份产物的 `__meta.userAgent` 均为 HeadlessChrome），
期间整机 1 分钟负载均值 4～9。

| 口径                              |           不窗口化（现状）            |             窗口化（P2）              |
| --------------------------------- | :-----------------------------------: | :-----------------------------------: |
| 首屏（第 15 行进 DOM）            |                6.185 s                |              **0.823 s**              |
| 全量（600 行进 DOM）              |             **19.866 s**              |               39.413 s                |
| 全量逐样本（ms）                  | 24166 / 21133 / 19866 / 19289 / 19642 | 39113 / 39413 / 43023 / 58953 / 37671 |
| 主线程阻塞（长任务超 50 ms 之和） |                8.132 s                |               37.772 s                |
| 长任务条数 / 单个最长             |              5 / 5.491 s              |             21 / 6.180 s              |

首屏确实从 6.2 s 提前到 0.82 s（7.5 倍），但**总时长 1.98 倍、主线程阻塞 4.64 倍**——
用户看到的不再是一次性等待，而是一段持续约 39 秒、每帧都堵一下的逐帧卡顿。

为什么在侧边栏成立的招数到管理页就反了（**机制部分是时序推断，没有直测**；可复现的事实只有上表）：

- 侧边栏的分片可代码级核对：列表是 `v-for` + `v-memo`，数组变长时旧条目整体跳过重渲染
  （`components/sidepanel/SidepanelAuthView.vue:603-606` 的 memo 依赖清单，理由见 600-602 的注释）。
- `el-table` 的 `data` 每换一次引用就走一次 `setData` → 表体按新数组重排。20 起步、每帧 +40 覆盖 600 行
  需要 15 帧，即 15 次 `setData`，累计约 5100 行 patch，相当于 8.5 次整表重排。
- 实测只涨到 1.98 倍而不是 8.5 倍，说明旧行那部分远便宜于行数相同的一次全新挂载
  （行 `row-key` 不变、呈现对象引用稳定，正是 P1 建立的那条纪律在起作用）；
  但绝对代价仍然足以把整段放开拖成 39 秒，且这期间页面一直在堵主线程。

处置：窗口化的实现与单测已删除（不留未接线的抽象），测量口径保留并回灌进 `mount` 场景——
`benchmarks/measure-options-perf.mjs` 现在一次采 `firstPaintMs`（第 15 行进 DOM）、
`wallMs`（全量进 DOM）、`maxLongMs`（单个最长任务），三个口径必须同时看：
只报首屏会把这次的分帧读成 7.5 倍提速，只报总时长又会漏掉它确实改善了首屏。**换定义等于换结论。**

另一次同构建的 mount 采样（label `attrib`，与上表不同批次：wall 15.9 s、68430 个采样帧）
给出下一步该攻的方向。self time 按采样数加权（前 14 项合计 51%，成本高度分散、没有单点大头）：

|     self time      | 归属                                        |
| :----------------: | ------------------------------------------- |
|        8.9%        | Vue 组件 `update`（渲染 effect）            |
|        7.0%        | 业务自身的渲染函数（`chunks/options-*.js`） |
|        6.0%        | `(program)`——浏览器侧 DOM 插入 / 样式与布局 |
|        6.0%        | GC                                          |
|    4.0% / 3.0%     | `mergeProps` / `updateProps`                |
| 2.5% / 2.5% / 1.8% | 响应式 `set` / `track` / 代理 `get`         |

JS 侧约两成时间花在"逐组件更新 + VNode props 处理"这条链上，也就是说**成本是「一次 flush 里的行数」
× 「每行的组件与 props 数」的乘积**，与文案解析、计算量基本无关。
可动的杠杆因此只剩两类——减少每行组件实例（操作列那 5 个 `el-tooltip` 是最可疑的来源，
Element Plus 的 tooltip 内部是一串 popper 组件链），或减少一次 flush 里的行数（分页 / 虚拟滚动）。
两者都会改变可感知的交互（悬浮提示样式、列表长度边界），按 `agents.md` 需先拍板。
"去掉 5 个 tooltip"的对照实验在 03:00 那组被整机负载污染（负载从 4 抬到 16，样本离散到
19.9 / 40.1 / 20.5 / 30.1 / 25.2 s，不足以出结论）；**04:36 已在同一时间窗内重采并出数，见 9.9**。

### 9.9 杠杆 B 定价：操作列 tooltip 的成本上限（2026-09-23 凌晨）

目的只有一个——在拍板之前，把"减少每行组件实例"这条路**到底能拿回多少**变成一个有对照的数字。
04:26–04:40 的 14 分钟内跑四批（表内三批，另 04:30 那批是下文单独交代的小实验；同一台机器、同一构建命令、
`--rows 600 --repeat 5 --fresh --only mount`，批间 CPU idle 稳定在 84～87%）：

| 批次（时刻）                   |    wall（整表进 DOM）    | 首屏（第 15 行） | 单个最长任务 | 阻塞之和 |
| ------------------------------ | :----------------------: | :--------------: | :----------: | :------: |
| 控制 `p3base`（04:26）         |   24272（19611…32560）   |       7586       |     6857     |  10263   |
| 实验 `exp2-notooltip`（04:36） | **14849**（13592…18741） |     **6095**     |   **5160**   | **8218** |
| 控制复测 `p3ctrl`（04:40）     |   28370（22176…37532）   |       7447       |     6627     |  10108   |

- **实验组只改一处**：操作列 5 个 `el-tooltip` 换成按钮上的原生 `:title`（`aria-label`、图标、`circle`、
  `size`、事件逐字不动）。其余代码与控制组完全相同。
- **两批控制的 wall 中位数差 17%（24.3 / 28.4 s）**，这就是本机当夜的漂移带；实验组 14.8 s
  的 5 个样本（13.6～18.7 s）**整段落在控制带下方**，且阻塞、最长单任务、首屏同向。
- **DOM 探针两侧逐字一致**：`domNodes 38655` / `buttons 3609` / `tags 1051` / `poppers 3` / `tableCells 6000`。
  也就是说这 40% 的差距**不来自少画了节点，只来自少创建了组件实例**——9.8 的成本模型在这里被独立验证了一次。
- 结论口径：`-40% wall / -20% 阻塞 / -20% 首屏 / -22% 最长任务` 是**完全去掉 tooltip 的上限**。
  任何保留悬浮提示的实现（例如全表共享一个 `el-tooltip` + 虚拟触发）只能拿到其中一部分，
  且要逐条验证显隐时序、焦点行为、`aria-describedby` 是否与今天一致——属可感知交互改动，需先拍板。

同一晚顺手否掉的另一个候选：**空关键词时短路 `SearchHighlight`**。想法是让每行少创建 4～6 个组件实例
（600 行即 2400～3600 个），且 DOM 与不短路时逐字相同（无命中时该组件只输出一个文本节点）。
实测 04:30 那批 wall 28881 / 首屏 8454 / 阻塞 11234——**方向甚至是反的，完全落在控制带内**。
量级也解释得通：它是"一个 computed + 一段 fragment"的纯文本组件，实例成本是微秒级，
撬不动以浏览器 DOM/样式与 EP 组件链为主体的秒级开销。**已回退，不留模板分叉**（4 处 `v-if/v-else` 的
复杂度换不到可测量的收益）。

测量环境的一条教训值得记下来：`03:00` 那组"负载从 4 抬到 16"的来源已经查到——
`mds_stores`（Spotlight 索引）在每次 `pnpm build` 之后飙到 55% CPU，而 `vm.loadavg` 是 1/5/15 分钟均值，
指数化的尾峰既会滞后也会放大。因此本轮起改为**先看 `top -l 2` 的 CPU idle、再看 loadavg**，
并在 `.output/`、`benchmarks/results/` 放置 `.metadata_never_index`（**该标记对启动卷是否真的生效未经验证**，
只是零成本尝试；真正起作用的是本批"控制复测夹住实验批"的设计）。

### 9.11 分页落地后的真机前后对比：曲线被压平，剩下的余量在数据层（2026-09-23 下午）

把 9.10 结尾那道二选一按第 2 条落地：管理页 `el-table` 的 `data` 恒为**一页**（默认 100，可选 50 / 100 / 200，

**测量口径的两处不得不改，先说清，否则下面的数字会被读错**

- 为什么用配对而不是"顺序跑三档"：当日 15:44–15:56 那三批（600→1200→2000 顺序跑）落在整机

**分页新引入的代价（这是净新增的一次交互，不是回归）**

- 一次翻页：主线程阻塞 `blocking` 560～762 ms、渲染进程脚本 19～68 ms、`rowReplaced` 2～3、
  节点数几乎不变（−16 ~ +1）；`wall` 读到的 1.2～1.5 s **不能当体感延迟读**——脚本自己的口径说明
  （第八节）里 `wall` 含 Node↔CDP 往返，而 `pageFlip` 的 `until` 尾部还固定睡 300 ms。
  按可比的主口径（长任务与 CDP 增量）看，翻页与同批的 `favorite`（1 125～1 266 ms）、
  `save`（506～1 071 ms）落在同一量级：**它不是新的高峰，只是多了一个原本不存在的交互**。
- **纯内存切片，零存储读、零解密**（`source.value.slice`），第六节担心的
  "Windows 慢磁盘下每次翻页一次整包 IO"确认不存在（`nodes` 增量 ±16 也侧证没有整表重建）。
- `save` 场景在**恰好 2000 条**的夹具上两次都超时失败——原因是总量上限拒写、对话框按设计保持打开并提示
  「因达到上限未保存」（`options.capacity.addBlocked`）。这条既是测量夹具的限制，
  也是上限语义在真机上被顺带验证过一次：达上限时新增不会静默失败。

**剩下的余量在哪里（P3 的定位据此收窄）**

分页之后 `mount` 仍有 3～5 秒，且这 3～5 秒与总条数无关（配对批次已证）。它落在**渲染面之外**：
扩展页启动 + 会话校验 + `storage.local` 整包读取与解密 + 应用骨架挂载。
DOM 探针在同一条证据里排除了渲染因素（三档节点数逐字一致）。
所以 P3（数据层削峰，第七节）现在的目标从"治大 Vault 卡顿"精确成"**削掉这 3～5 秒的固定底盘**"，
而不再涉及渲染行数；配额墙与整包 IO 的口径见 [ARCHITECTURE.md](./ARCHITECTURE.md)「数据层大 Vault 成本与改造路线」。

### 9.12 深度评审后的收尾五项（2026-09-24，全部不改外部行为）

对上面整批改动做四轴评审（规范 / 规格 / 安全 / 性能）后，落地的收尾都属"结构与口径"，
不含任何用户可感知的变化。逐项记在这里，避免后来人把这些当作"顺手重构"再改回去。

1. **分页纯计算下沉**：`PAGE_SIZE_OPTIONS` / `DEFAULT_PAGE_SIZE` / `PaginationPagerItem` /
   `pageForSizeChange` / `buildPagerItems` 从 `composables/useVaultListPagination.ts` 移到
   [utils/vaultPagination.ts](../utils/vaultPagination.ts)，composable 只留响应式状态与两个 watcher。
   理由是 agents.md 的技术栈边界（纯函数与无状态算法放 `utils/`，composable 负责响应式与副作用），
   实际收益是页码折叠与换档落点这两套规则可以在 `tests/utils/vaultPagination.test.ts` 里
   不挂组件直接单测。**外部行为逐字不变**：函数体一行未改，只是搬位置 + 拆测试文件。
2. **`PasswordTable` 不再交出 EP 表格实例**：`defineExpose` 从 `{ tableRef }` 改成两个意图方法
   `clearSelection()` / `applySort(prop, order)`，EP 实例的判空收进组件内部。调用点
   （`entrypoints/options/App.vue` 的选择归零 watcher 与排序恢复）随之改为意图调用；
   `tests/architecture/optionsRenderIdentity.test.ts` 的那条补偿接线守卫同时加了一条反向断言
   ——App.vue 里不得再出现 `passwordTableRef.value…tableRef`。
3. **两个导入弹窗的额度接线收口**：`useImportCapacity` 新增 `takeImportableEntries()`

   `ImportCapacity<T>`，以及两个纯文案选择函数 `importSuccessMessage` / `importFailureMessage`
   （原先在两个弹窗里各写一遍同样的 i18n key 与容量错误判别）。
4. **外部关键词只收口一次的地方不再各写一份**：`useRuntimeMessageHandler` 的

   单点定义。回归：`tests/composables/useRuntimeMessageHandler.searchKeyword.test.ts` 的超长截断用例。
5. **基准可比性与守卫牙齿**：`warmPinyinMatcher()` 翻的是模块级就绪标志且在收集阶段完成，
   顶层 `await` 会把同文件的侧边栏基线从"纯子串"变成"每字段问一遍拼音"——§3.1 那张表因此不可比。

   （`} aphid` / `${` 相邻的模板插值形态——正是第二版漏掉的 `backup${n}.aphid${ts}`），

## 十、对 issue #89 的处理建议

- **不建议直接合入用户 fork 的分页 PR。** 它把第五节 5 个真缺陷原样留在原地（分页后仍按 50 行整表重渲染），
  并要求重新定义跨页选择语义。窗口化被否决之后，分页是"减少一次 flush 里的行数"这一类里成本最低的一种，
  但它是方案 A 的实现细节而不是主方案——更合理的形态是把它作为**可选偏好项**（"每页条数"，默认不分页），
  而不是改变所有人的默认列表行为。

  > **落地状态（2026-09-23 下午，见 9.11）**：这条建议的两处判断，一处已过期、一处仍然成立。
  > ① "5 个真缺陷原样留在原地"这个反对理由已经消失——它们在 P1 与轮四里被逐个修掉了（9.1、9.4、9.10），
  > 分页落地时按行数结算的那部分成本已经不存在；② "默认不分页"这一形态**未被采纳**：定在 2000 条上限之后，
  > "不分页"就是那条 180 秒的路径，把它留作默认等于让绝大多数用户继续走最贵的一条。
  > 现在的形态是**分页恒开**、每页 50/100/200 可选、默认 100，且**刻意不设"全部"档**。
  > 跨页选择语义按 9.11 的方式重新定义（选择集跨页保留 + 显式报差额），而不是切页清空。

- 可直接粘贴的回复草稿（中文）：

  > 600 条这个量级我们这边复现并定位到了：卡的主要不是"数据多算不过来"（实测 600 条的过滤+排序只有
  > 1～5 毫秒），而是"600 行一次性全渲染 + 每次交互重排整张表"。所以单纯加分页只能解决一半，

  > 点新增阻塞时间降 60%），这些改动不改变任何交互。
  > 剩下的"打开管理页时 600 行一次性铺开"我们试过分段渲染（先出一屏、随后逐帧补齐），
  > 真机实测在表格组件上反而使总耗时翻倍，已经回退。随后我们改从"每行挂了多少组件"下手：
  > 把操作列那 5 个按钮的悬浮提示从"每行 5 个实例"换成"全表共享 1 个实例"（页面 DOM 一个节点都不少），
  > 600 行首屏整表挂载耗时实测降了约一半，悬停延迟、隐藏时序、移入浮层保持显示、无障碍关联这些
  > 观感和改前逐条一致——这条已经在下个版本里了。

  > 搜索、只看收藏、标签筛选或排序口径变化会回到第 1 页（和"命中 M 条"这个读数保持同一批内容）。
  > 分页只决定一次呈现多少行，条目总数、排序口径和数据本身都不受影响。

### 12.4 部分暂存的操作规程（本仓库踩过的坑）

`.husky/pre-commit` 跑 `lint-staged`（`eslint --fix` + `prettier --write` + `stylelint --fix`）。对**部分暂存**
的文件，它会 stash 未暂存 hunk、格式化索引版本、再恢复——历史上有把另一会话未提交的改动整块回滚的先例。
因此：

- 每个混编文件提交后立即 `git diff -- <file>` 与提交前的 hunk 清单逐条比对，确认他波 hunk 仍在工作树；
- 一次只处理一个提交，不要把多个混编文件同时留在部分暂存状态；
- 若 hook 报格式改动，先看 `git status` 是否多出未预期的文件，宁可中止本次提交再排查，不要重试提交。

### 12.5 提交后验证顺序

`pnpm typecheck` → `pnpm lint` → `pnpm lint:style` → `pnpm exec prettier --check <本次文件>` →
`pnpm exec vitest run`（全量）→ `pnpm build` → 真机 `pnpm exec playwright test e2e/pagination.spec.ts e2e/operation-tooltip.spec.ts`
（注意 `pnpm test:e2e -- <file>` 与 `pnpm test:run -- <file>` 都**不做过滤**，必须用 `pnpm exec playwright test <path>`）。
