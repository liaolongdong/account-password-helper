## 一、结论先行

1. **这是本议题里唯一的「真找回」**，也是唯一引入**第二种永久密钥材料**的方案：
   恢复码泄露 = 全库离线可读，且**改主密码撤销不了**（重包裹沿用同一枚码）。
   因此撤销 / 轮换能力必须与实现**同期**交付，不允许后补。
2. **找回后必然要走一次「不依赖旧主密码的 rekey」**，这是本方案的第二处密码学改动，也是它
   不像看起来那么小的真正原因：数据密钥由主密码确定性派生，用户设新主密码 = 换一把数据密钥
   = 五个加密域整库重加密。若只做到「用恢复码解出旧数据密钥」就收工，用户会卡在
   「进得去但再也改不了主密码」的死路里。
3. **会话侧不需要新写密钥落盘逻辑**：`prepareSessionRekey(dataKey, validityHours)`
   本来就接受**数据密钥而非主密码**（[sessionManager-storage.ts:665-693](../../utils/sessionManager-storage.ts)），
   恢复解锁只要复用它 + 既有的 `adoptRekeyedSession` 自愈监听。
4. **存量用户可在已解锁态一键补生成，零重加密**：只需 `getSessionDataKey()` 取当前数据密钥、
   随机生成恢复码、写一个 blob。这是本方案最实在的成本优势。
5. **包裹对象必须是数据密钥，绝不是主密码**。把主密码加密一份落盘（哪怕用恢复码包裹）
   等于把仓库已经明确废弃的反模式请回来——`session_master_password` 那个键的注释写着
   「现已废弃——主密码不再落盘」（同文件 `:30-33`）。

## 二、要解决的问题与验收口径

| 视角                 | 今天的处境                                                           | 本方案要达到                                                         |
| -------------------- | -------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 忘记主密码的用户     | 只剩 `clearAllData()`，整库不可逆清空                                | 用事先保存的恢复码解密数据密钥 → 重设主密码 → 数据留下               |
| 从没导出过备份的用户 | 无任何退路                                                           | 设置主密码当页就把「抄一次恢复码」摆在面前（可跳过，但必须显式跳过） |
| 攻击者（拿到磁盘）   | 会话期内已可解密（评测文档 §1 判据 3/4）；会话已锁时只能爆破 600k 轮 | 不新增该面；恢复码是 256-bit 随机值，离线不可爆破                    |
| 项目自己             | 「无法找回」写进 15 个手写对外文件                                   | 口径改为「默认无法找回；**已登记恢复码的用户例外**」，双语同步       |

**一句话验收**：忘记主密码后，凭恢复码能在**不丢任何一条数据**的前提下换上新主密码并正常使用；
没有恢复码的用户，行为与今天完全一致。

## 三、硬约束（来自 `AGENTS.md`，不可协商）

- 不落盘主密码、不落盘恢复码本身、不落盘任何可由它们推导的中间量；日志走 `utils/logger.ts` 且不含敏感字段。
- PBKDF2 轮数必须 `import` 自 [cryptoParams.ts](../../utils/cryptoParams.ts)，
  就地写一份 `600000` 会被 `tests/architecture/securityDefaults.test.ts` 判红（它同时钉「值」与「定义处唯一」）。
- 新增加密容器必须**版本化**、必须**保留旧数据兼容**（无 blob = 存量用户，功能整体不可见而非报错）、
  必须有失败回滚路径，并补齐「成功 / 失败 / 旧格式 / 边界」四类测试。
- 不得改变 `.aph` / `.aphid` 容器（`version: 1`）与字段密文格式。
- 不得改变 `WRAP_KEY` / `WRAPPED_DATA_KEY` 的落盘形态——那是「重启浏览器保持登录」的实现依赖
  （见 §八 的否决线 M-0）。

## 四、blob 的形状与派生

blob 存于 `chrome.storage.local` 新键（建议 `recovery_key_config`，命名对齐 `master_password_config`），
形态是 **JSON 对象而非字节容器**：

```ts
interface RecoveryKeyConfig {
  v: 1; // 容器版本，与 .aph 的 BACKUP_VERSION 各自独立演进
  kdf: 'pbkdf2-sha256';
  salt: string; // 16B 随机 → hex，明文，仅做域分离与抗彩虹表
  wrappedDataKey: string; // Base64(iv[12] ‖ AES-GCM(数据密钥 hex))，认证标签即恢复码的正确性证明
  createdAt: number; // 仅用于「这枚恢复码是啥时候登记的」展示
}
```

- **为什么用 JSON 而不是复用 `.aph` 的字节布局**：`.aph` 是要离开扩展、跨机器、可能被别的实现解析的文件，
  紧凑字节容器有意义；blob 只在本扩展的 storage 里活，带 `v`/`kdf` 的自描述对象在将来抬版本时
  不必靠长度嗅探。两条路径**不共用代码**，避免把文件容器的解析闸门（`MAX_PASSWORD_IMPORT_INPUT_BYTES` 那套）
  误当成 storage blob 的边界。
- **派生必须域分离**：`keyR = PBKDF2(恢复码, salt='aph-recovery|' + blob.salt, 600k) → AES-256-GCM`，
  与 `deriveVerifierHash`（前缀 `aph-verify|`）、`deriveEncryptionKey`（裸 salt）三者互不相通。
  沿用 [encryption.ts:108-117](../../utils/encryption.ts) 的写法新增一个 `deriveRecoveryKey`，
  不要往 `deriveEncryptionKey` 上加参数（它是密码与会话边界上的函数，签名变化会波及全部调用点）。
- **正确性判据只有一个**：GCM 认证标签。校验值解不开就是恢复码错，不需要额外存一份 hash
  （多存一份 = 多一个可被离线爆破的靶子）。
- **恢复码形态**：256-bit 随机，展示为分组 base32（Crockford 字母表，剔除易混字符），
  输入侧先归一化（大写、剥分隔符、字符集与长度校验）**再**进 PBKDF2——
  typo 要能在 0ms 内被拒，不该让人白等一次 600k 轮。

## 五、三条路径

### 5.1 登记（存量与新用户同一条）

前置：会话有效（拿得到 `getSessionDataKey()`）。

1. 生成 32B 随机 → 展示 base32 分组，**同时只展示这一次**；
2. 用户确认已抄存（必须勾选「我已保存到库外的地方」才继续，勾选状态不落盘）；
3. 派生 `keyR` → 包裹数据密钥 → 单次 `set()` 写 `recovery_key_config`
   （只写这一个键，**不与数据同批**，因此不存在 §10.5 那类整数组覆写竞态）；
4. 展示「已登记 · 何时 · 可轮换 / 可撤销」。

已存在 blob 时入口变成「轮换 / 撤销」，不静默覆盖。

### 5.2 找回（解锁页第二条入口）

1. 输入恢复码 → 归一化 → `keyR` → 解出数据密钥 `K_old`；
2. 用 `prepareSessionRekey(K_old, validityHours)` 建立会话密钥材料，
   并按 `createSession` 的同一顺序写 `storage.session` → `storage.local`（原子同批）→
   `ensurePasswordsEncryptedAtRest()` → `SESSION_LOCK_STATE` 镜像；
   **实现方式**：把 `createSession` 的后半段抽成
   `createSessionWithKey(dataKey, validityHours)`，`createSession(mp, hours)` 变成
   「派生 + 调用它」的薄壳。**逐条对齐现有写入次序与清理动作**（含
   `chrome.storage.local.remove(SESSION_STORAGE_KEYS.MASTER_PASSWORD)` 与
   `waitForBrowserStartupRelockBeforeAuthentication()` 门禁、以及失败时的 `clearSession()` 回滚），
   顺序变了就会击穿 B6 代际保护；
3. 强制引导设新主密码（见 5.3）；用户坚持跳过也允许，但会话内每次进入管理页都提示「主密码仍是已遗忘的那把」。

### 5.3 换钥（`rekeyFromDataKey`）

今天 [changeMasterPassword.ts:70](../../utils/storage/changeMasterPassword.ts) 的第 1 步是「验证旧密码」。
新增一条**同函数内的**分支：调用方已经提供了 `K_old`（恢复码路径），跳过旧密码验证、
直接进第 2 步起的解密 → 重加密 → 原子覆写。要求：

- 第 10.5 步的**五域快照复验**、第 11 步的**单次原子 `set()`**、写失败时的 `clearSession()` 处置，
  一字不动地复用；
- 原子写里**必须一并**带上新重包裹的 `recovery_key_config`（同批！否则出现「新数据密钥落盘、
  恢复码仍指向旧密钥」的死 blob，恢复码从此解不开）；
- `salt` 沿用现有值（与既有注释同一理由：换钥不换 salt，否则后续解密派生出不同密钥）。

## 六、撤销、轮换与失效时机

| 动作                  | 语义                        | 要点                                                                                             |
| --------------------- | --------------------------- | ------------------------------------------------------------------------------------------------ |
| 轮换                  | 生成新码、重包裹、覆盖 blob | 旧码立即失效；提示「旧码作废」并要求确认                                                         |
| 撤销                  | 删除 blob                   | 明确写出后果：撤销后重新回到「忘记即清空」                                                       |
| 重置 / `clearAllData` | 随全库消失                  | 已被 `useAuthFlow.resetMasterPassword` 的 `lockSession → clearAllData` 覆盖，无需新增清理点      |
| 换机 / 全新安装       | blob **不随 `.aph` 走**     | 恢复码只对本机这份库有效；导入恢复的是数据，不是恢复码。新机器需重新登记，必须写进帮助与对外文档 |

## 十、明确不做

- **不包裹主密码**（评测文档档位 B'）：会把「主密码绝不落盘」这条已收口的边界重新打开。
- **不做人类可读的助记词 / 自拟恢复口令**：熵由用户决定 = 离线爆破面由用户决定。只发机器随机码。
- **不做云端 / 邮件 / 短信投递恢复材料**：违反本地优先；投递即外传。
- **不做「会话有效期内免旧密码改主密码」**（评测文档档位 C）：那是把攻击面从就地读升级为可导出带走，属独立安全议题。
- **不在 `.aph` / `.aphid` 里塞恢复码**：文件是要离开这台机器的，等于把万能钥匙复制一份。
