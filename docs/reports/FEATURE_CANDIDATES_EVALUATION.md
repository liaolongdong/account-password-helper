## 1. 怎么确认「当前不存在」

不靠印象，靠可复算的检索。以下每条候选的「现状证据」都出自同一套动作：

- 全仓 `git grep`（`*.ts` / `*.vue` / `*.json` / `*.css`）搜能力名与 API 名：
  `webauthn`、`PublicKeyCredential`、`passkey`、`kdbx`、`opvault`、`hibp`、`haveibeenpwned`、
  `prefers-color-scheme`、`emergency`、`recoveryCode`、`恢复码`。
  命中为 0 的才算「不存在」；命中的要么归到 §2（已实现），要么归到 §3（刻意排除）。
- 读 `utils/types.ts` 的 `PasswordEntry`、`utils/identity/types.ts` 的 `IdentityPayload`、
  `utils/storageKeys.ts` 的键清单、`utils/passwordSort.ts` 的默认排序——这四张表摆在那里，
  「还有哪些字段/档位没有」这类问题基本不需要猜。
- 读 `docs/ARCHITECTURE.md`「功能实现详解」的 31 个小节标题，作为「已交付能力」的权威清单。
- 只有代码不够的地方（例如「忘记密码」到底怎么走）顺着调用链读到实现，不看文案。

一处诚实的限制：`prefers-color-scheme` 在 `assets/theme/tokens.css` 与所有入口里为 0 命中，
但官网 20 个对外页面在 `3539e0d` 之后已经跟着系统配色了。也就是说 C3 的不一致
**是这一轮新造出来的**，不是历史遗留。

## 4. 候选清单（六条）

### C1 生物识别 / PIN 快捷解锁（WebAuthn 平台认证器作访问守卫）

- **痛点**：解锁是全产品最高频动作，会话过期后必须重输主密码；而主密码刻意做得长。
  现状证据：全仓 `webauthn` / `PublicKeyCredential` 命中 0。
- **方案要点**：生物识别**只做验证因子，不做密钥材料**。数据密钥仍由「主密码 + salt」经
  PBKDF2(600k) 派生；Touch ID / Windows Hello 的结果只决定是否放行一次既有解锁路径。
  敏感操作（换钥、导出、重置）永远走主密码。
- **必须正面处理的既有约束**：`utils/sessionManager-storage.ts:45` 那份内存镜像（磁盘上
  `WRAPPED_DATA_KEY` 密文的副本）与 `:49` 的数据密钥热缓存（与 `storage.session` 互为镜像）
  是「重启浏览器保持登录」这条承诺的实现依赖。任何「把密钥挪进内存 / 挪进 storage.session」
  的顺手改动都会废掉这条承诺，并造出「会话有效但列表为空」的新缺陷。所以 C1 只能加在
  **解包之前的守卫**位置，不能改密钥的存放形态。
- **降级路径**：无平台认证器 / 用户验证失败 / 新设备 → 回主密码，且必须与既有
  `sessionLock`、`browserStartupRelock` 的代际保护共存（不能出现「生物识别成功但代际过期」）。

### C2 主密码找回材料（离线恢复码）

- **痛点**：今天忘记密码的唯一出路是「重置全部数据」，即清空整库
  （`auth.forgotPassword` 文案 + `composables/useAuthFlow.ts:323` 的 `clearAllData()`）。
  对普通用户这是不可逆的数据丢失。
- **方案要点**：导出时随机生成一枚高熵恢复密钥（不进人类可读短码那一类），
  用它单独包裹数据密钥，密文与主密码包裹的并存；找回时用恢复码解包，再用新主密码重包。
  全程离线，不落任何服务端。
- **代价**：这是**新增一种密钥封装格式**，直接落在 agents.md 的「必须谨慎」区——
  要版本化、要旧数据兼容、要失败回滚、要「成功/失败/旧格式/边界」四类测试齐全。
  同时必须重新设计「恢复码泄漏 = 全库可读」的用户教育，隐私说明与帮助文案都要改。

### C3 扩展侧「跟随系统」配色（第 7 档主题）

- **痛点**：官网 20 个页面已经自动跟随系统明暗，扩展 UI 仍是 6 档手动主题，
  两处观感在 2026-10 之后开始分叉。
- **现状证据**：`assets/theme/tokens.css` 与全部入口里 `prefers-color-scheme` 命中 0。
- **代价与风险**：不是纯内部改动——它是**新的用户可见设置项 + 默认可见行为变化**，
  且 6 档主题各自要有一套可用的暗色映射（`--aph-*` 令牌需要翻倍，Shadow DOM 内联写入的
  令牌集合同步跟着改，浮球/内联下拉在 host 页面里的对比度要重新量）。按 agents.md，
  这类改动必须先让用户在「保持手动 6 档」和「加一档跟随系统」之间拍板。

### C4 Passkey 凭据管理

- **方向正确，工程极大**：需要 WebAuthn 注册/断言、与 relying-party 的 `navigator.credentials.get()`
  流程协作、以及「凭据存在哪、如何备份、如何跨设备」的模型（这三问又把 C2 和同步问题拉回来）。
- **当前不可替代**：填充路径完全不受影响，Passkey 不覆盖存量密码站点。
- **结论**：列为下一个大版本议题，本轮不排。

### C5 安全体检分数历史与趋势

- **痛点**：体检是一次性读数，用户不知道「比上个月好还是坏」；备份提醒已经有
  `last_verified_backup_at` 这类时间戳先例。
- **现状证据**：`utils/storageKeys.ts` 无健康度历史键；`utils/passwordHealth.ts` 只算当前分。
- **成本形态**：新增一个「每次体检写一条摘要」的键（只存分数与计数，**绝不存条目内容或明文**），
  options 侧一张趋势图。风险面小，收益偏「留存与可信度」而非功能覆盖。

### C6 站点规则收到「行为粒度」：按站点覆盖填充模式 / 悬浮按钮 / 匹配档位

- **痛点**：用户想的是「这个站别自动弹侧边栏，但保留内联下拉」「这个站别长匹配」。
- **现状证据（粒度对不上，不是没有规则）**：
  - `SiteRule` 只有两个可写字段——`customSelectors` 与 `penetrateShadow`
    （`utils/storage/siteRules.ts:23-35`），即「字段选择器 + 影子穿透」。
  - 走侧边栏还是内联是**全局** `fillMode`（`utils/types.ts:395`，默认见
    `utils/storage/configManager.ts:226`，并对 `undefined` 做过存量保护补丁 `:253`）。
  - 悬浮按钮显隐、跨子域匹配档位同为全局（`FLOATING_BUTTON_CONFIG` / `DOMAIN_MATCH_CONFIG`）。
  - 唯一已经是域名级的只有自动保存黑名单（`utils/storage/autoSaveManager.ts:88-138`）。
- **成本形态**：给 `SiteRule` 加**可选**字段（缺字段 = 沿用全局），而不是新造一套规则系统；
  消费端读规则的地方已在 `FormDetector.init()` 首轮等待 `siteRuleReady` 之后，
  匹配档位必须按 `resolveMatchTier` 的既有口径显式传档，不能新增一次全库读取。
- **必须先回答的设计问题**：站点级 `fillMode` 覆盖全局默认时，谁赢、怎么在设置里看得见这条覆盖——
  这是用户可见行为，按 agents.md 要停下来问，不能默认「站点级总是赢」。

## 5. 取舍矩阵

标记口径：**价值**=痛点强度 × 频次；**成本**=工程量（低 ≤2 人日、中 ≤1 周、高 >1 周，粗档）；
风险与契合度按「会不会碰到安全边界 / 会不会违背公开承诺」判；
**SLA** 一列专指 agents.md 里的侧边栏秒开与管理页首屏三段承诺。

| 候选              | 价值         | 成本  | 安全/会话风险              | 数据兼容风险                  | 权限与商店合规           | SLA                            | 本地优先契合   | 结论档                         |
| ----------------- | ------------ | ----- | -------------------------- | ----------------------------- | ------------------------ | ------------------------------ | -------------- | ------------------------------ |
| C1 生物识别解锁   | 高           | 中-高 | **高**（会话与密钥路径）   | 低（新增守卫，不动密文格式）  | 需更新隐私说明；无新权限 | 守卫不能进解锁关键路径，需实测 | 契合           | **优先做设计，不做实现**       |
| C2 主密码找回材料 | 高           | 高    | **高**（新增密钥封装格式） | **高**（存储/备份格式版本化） | 需重写隐私说明与帮助     | 解锁路径多一步，需实测         | 契合           | 排在 C1 之后，先解 C1 的高频痛 |
| C3 跟随系统配色   | 中           | 中    | 低                         | 无（不进存储结构）            | 无                       | 主题切换不能拖累首帧           | 契合           | **等用户拍板**（可见行为变化） |
| C4 Passkey 管理   | 中（长期高） | 极高  | 高                         | 高                            | 商店审核不确定           | 不相关                         | 契合但需新模型 | **暂缓**（大版本议题）         |
| C5 体检趋势       | 中           | 低    | 低（只存摘要，禁存内容）   | 低（新键，旧数据无迁移）      | 无                       | 体检本身不在热路径             | 契合           | **可插队，最便宜的收益**       |
| C6 站点规则细化   | 中           | 低-中 | 低                         | 低（规则内加档位，向后兼容）  | 无                       | content 侧不得新增全库读       | 契合           | 可与 C5 同波                   |

一句话读法：**唯一同时具备「高频痛点 + 可控成本」的是 C5/C6；唯一值得为它先写安全设计稿的是 C1；
C2 是 C1 的连带问题（守卫做不好，用户更依赖找回材料）；C3 卡在决策不在工程；C4 不在这轮。**

## 6. 前置动作（谁都不许跳过）

1. C1 与 C2：先产出安全设计方案（密钥流图 + 降级矩阵 + 测试矩阵），经用户确认后才谈实现；
   任何触碰 `utils/encryption.ts` / `utils/sessionManager*.ts` / 存储结构的改动，
   按 agents.md 必须保留旧数据兼容与失败回滚路径。
2. C3：属用户可见设置项与默认可见行为变化，必须先询问，不得随本轮落地页改动一并「顺手做」。
3. C5/C6：可直接进入实现评估，但仍需各自补回归测试（C5 断言「历史条目不含任何条目内容」；
   C6 断言「规则缺失/旧形状时行为与今天一致」）。
4. 任何一条落地时，文档同步按 agents.md 的矩阵走：README / README.en / ARCHITECTURE(.en) /
   侧边栏 HelpDialog 词条 / CWS 正文 / `wxt.config.ts` 描述 / 两套 i18n 的中英 key 一致。
