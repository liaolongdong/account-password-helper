## 一、结论先行

1. **E1 是当前实测到的最大单项杠杆，但它只治写侧。** 保存 1 条的 IO 全貌（`rmw`）在 2000 条时为 **263.1 ms**、5000 条时 **941.8 ms**；分键后同等动作落在 `setSmall` 档：**0.8 ms / 1.6 ms**（约 **150×**）。首屏侧 E1 不但没有收益，全库冷读还贵 **+33%～58%**（09-25 M-6 同窗口配对：@2000 SW **+33% / +9.9 ms**、options **+39% / +12.1 ms**）——但绝对值只是**每次加载多付约 10～12 ms**，量级上不影响首屏结论：首屏 < 1s 由分页（已落地）与快照/SW 缓存承担，**不要把它记在 E1 账上**。

   > **150× 的前提条件（09-25 M-5 实测补上的）**：它只在**索引键不必每次保存都重写**时成立。88 KB 索引键单写实测 **9.8 ms**（@2000，同窗口 `setSmall` 0.3～0.7 ms），若按本稿 §5.1 原样「条目键与索引键每次都同批写」，新增一条的真实写成本是 **11.4 ms = 14×**，不是 150×。把索引写收窄到「id 集合真的变了」（新增 / 删除 / 重排）之后，编辑与保存路径才落回 `setSmall` 档 —— 这条修正写进 §5.1，是本稿相对初版唯一因测量而改变的结论。

2. **E1 的迁移不需要解密、不改变密文格式。** 一条 `EncryptedPasswordEntry` 是自包含对象（`utils/encryption.ts:263-285` 按字段加密，`id`/`order`/`tag`/时间戳本就是明文），把「一个 N 元素数组」改成「N 个键各存一个元素」是**纯结构搬运**：不派生密钥、不触碰 AES、不动 `.aph` 备份格式。这是 E1 与 C1/C2（at-rest 密文格式）最本质的区别，也是它可以「双写 + 对账 + 可回滚」的原因。
3. **E1 的真实代价不是性能，是三件事**：① 跨键一致性（今天靠「一次 `set` 写 2～5 个键」的原子性保证，见 `trashManager.ts:88-91`、`changeMasterPassword.ts:154-165`）；② **扇出语义重写**（三个上下文的 `onChanged` 快路径全部假设 `changes[account_passwords].newValue` 是整包数组）；③ 未验证的**键数上限与部分失败语义**。
4. **本稿推荐落点：主库按条目分键 + 单独索引键，回收站/历史/身份/快照四处本轮不动**（对应数据层报告第八节第 2 条的选项 (b)）。理由见第四节末。
5. **第五节的前置测量已全部跑完（09-25，M-1 … M-6）**，其中「一次 `set` 写 2000 个键」结果为**全落**（无上限、无截断、无部分成功），§5.2 的否决线未触发。剩下唯一未测的是 M-4（Windows 放大倍数，本机不可得），它只影响倍数、不影响方向。

## 二、要解决的问题与验收口径

### 2.1 问题定义（用户视角）

| 动作                         | 今天（2000 条，实测/推算分段）                                    | 阈值         | 谁负责达标                                |
| ---------------------------- | ----------------------------------------------------------------- | ------------ | ----------------------------------------- |
| 打开管理页                   | 全库读 43.8 + 全库解密 410.6 + 分页后只渲染 100 行                | **< 1 s**    | 分页（已落地）+ P0-1/P0-3，**不是 E1**    |
| 添加 / 保存 1 条             | `rmw` 263.1 IO + 5 次 AES ≈ 2 ms + 快照重加密 3.9 + 扇出 211～245 | **< 50 ms**  | **只有 E1**（P0/P1 都碰不到 IO 与投递段） |
| 过滤 / 搜索 / 排序           | 命中集计算实测个位数毫秒（渲染层报告 3.1），渲染受分页保护        | 无可感知停顿 | 分页 + `keywordMatch`，与 E1 无关         |
| 批量改标签 / 收藏 / 使用痕迹 | 一次整包写 + 一次整包载荷投递；P0-3 后外部写入侧可零解密就地修补  | 无可感知停顿 | P0-2/P0-3 已吃大头，E1 吃剩下那笔整包写   |
| 导出 / 备份                  | 读整库解密（410.6）+ 内存组装，无写放大                           | 无可感知停顿 | 与 E1 无关                                |

**一句话验收**：E1 若落地，唯一必须被它拿下的指标是「保存/新增 1 条在 2000 条库上 P50 < 50 ms」。其余指标 E1 只允许**不倒退**（全库读涨幅 ≤ 25%、整库重写涨幅 ≤ +20%、首屏仍 < 1 s）。

### 2.2 硬约束（来自 `agents.md`，不可协商）

- 不改 `.aph` 备份/导出格式，不改导入模板，不改加密算法、KDF 参数、密文编码 —— E1 只改**「一个逻辑集合摊到几个 storage 键上」**。
- 迁移必须保留旧数据可读、必须有回滚路径，并且**成功 / 失败 / 旧格式 / 边界**四类测试齐备（第七节矩阵）。
- `storage.local` 中任何时刻不得出现比今天更多的明文（第十节风险 3 专门处理迁移窗口的双写副本）。
- 不与 P0 混在一个提交批次；E1 自身按第五节批次拆分。

## 三、键结构选型

### 3.1 三个候选形态

单位 ms，取自数据层报告 4.2 的 options 侧实测（600 / 2000 / 5000）。
**「全库读」这一列要按 §5.3 的 M-6 读**：那是 13 B 短键名口径，且三档涨幅是 +22% / +52% / +16%（不是一个笼统的 16%）；
换成提案里的真实 49 B 键名后同窗口配对复测为 **+33%～58%**（四格各自：@2000 SW +33% / options +39%，@5000 SW +45% / options +58%），绝对值 @2000 = 31.4 → 43.5 ms。

| 形态                        | 一次 set 的键数 | 保存 1 条写成本  | 全库读         | 整库重写     | 主要风险                                     |
| --------------------------- | --------------- | ---------------- | -------------- | ------------ | -------------------------------------------- |
| **S0 现状**（单键整包）     | 1               | 63.7 / 245.9     | 43.8 / 175.1   | 63.7 / 245.9 | 无                                           |
| **S1 每条一键**（本稿推荐） | 1 + 索引        | **0.8 / 1.6**    | 66.7 / 202.8   | 90.9 / 240.0 | 键数上限已过 M-1；冷读涨幅见上；扇出改动最大 |
| **S2 每 200 条一块**        | 1 + ⌈N/200⌉     | 未实测（~96 KB） | 未实测（≈ S0） | ≈ S0         | 块内丢更新窗口大于 S1；收益只有 S0→S1 的中间 |

`shardsAll`（整库按条目分键重写）2000 条时 90.9 vs 整包 63.7 —— 这是**改主密码 / 恢复备份 / 全量导入 / 拖拽重编号**的最坏情况，涨幅 +43%；数据层报告在 5000 条口径下给出的对照是 240.0 vs 245.9（基本等价）。两个规模结论一致：**最坏情况不进质量级，仍在线性可接受区间**。

### 3.2 为什么选 S1 而不是 S2

S2 的收益是「写放大 ÷ 200」，但它的**语义复杂度与 S1 完全一样**（索引、跨键一致性、扇出改写、迁移，一个都不能少），却拿不到 S1 的「`changes` 只含被改条目 → 各上下文天然知道哪一条变了」这条结构性红利（数据层报告第七节 P2 段：这条红利正是 P1「变更票据」想要而拿不到的性质）。既然复杂度同价，取收益上界。

### 3.3 具体键名（提案）

```text
account_passwords_index      → { v: 1, ids: string[], count: number, rev: number, migratedAt?: number }
account_passwords.item_<id>  → 单个 EncryptedPasswordEntry 对象（结构与今天数组元素完全一致）
```

设计要点：

- **元素结构零改动**：`{...entry, username: <cipher>, ..., encrypted: true}` 原样搬到键值，不做字段重排、不加包装数组。这让「读一个键 → 解一个条目」与今天的「读整包 → 解第 i 个元素」逐位等价，现有 `decryptPasswordEntry` 与 `undecryptableCount` 语义原样保留。
- **`id` 进键名**：`chrome.storage.local.get(key)` 按 key 取，单条读不必扫描全库；这也是 `updatePassword(id)` / `updatePasswordInSession(id)` 从现在起不必再读整包的原因。
- **索引键必选**：`get()` 无参虽可取全部，但会把回收站/历史/身份/提醒一起拉进来；`getKeysByFilter` 在 MV3 已不推荐。索引键体积要按真实 id 形态算：`generateId()` 产出 `'uuid-' + UUID` 即 **41 字符**（`utils/generateId.ts:10-15`），2000 条的 JSON 数组约 **88 KB**。它是「比条目键大两个数量级的小键」——09-25 M-5 用 41 字符假 id 造出 **88,036 B** 的索引对象实测：单写 **9.8 ms**（@2000，SW 与 options 两上下文同值），5000 条（220,036 B）**44.8～58.9 ms**；同日 M-6 补上读侧：单键 `get` 回这个 88 KB 对象 **1.4～1.9 ms**（@2000）/ 3.2～3.6 ms（@5000），**稳态下区域里已有 2000 个分片键时读数不变**（批量写完之后的那一次读除外，见 §5.3 M-6 结论 1）。它确实落在 `setSmall` 0.8 ms 与 `setAll` 63.7 ms 之间，但**离 `setSmall` 有两个数量级**，所以索引键**不能**被当成"顺手带一下"的键：见 §5.1 的收窄。
- **`rev` 只做诊断，不做锁**：每次结构变更 +1，用于对账与「迁移后校验」，不引入乐观并发失败路径（今天整包写同样是 last-write-wins，S1 不比它更弱）。
- **不引入 `account_passwords` 之外的新权限、不改 `permissions`/`host_permissions`。**

### 3.4 配额口径（必须写清，避免被当成"存不下"的解药）

`chrome.storage.local` 配额是**总量**口径：探针运行时读到 `local`/`session` 各 10,485,760 字节、`hasUnlimitedStorage: false`（数据层报告第十节第 3 条）。分片**不提高总量上限**，且键名与索引本身要计字节：键名 `account_passwords.item_` + 41 字符 id ≈ 64 B，2000 个约 **128 KB**，再加 88 KB 索引键 —— 相对 10 MB 是 2% 量级，**可接受但不是零**，且 Chrome 是否把键名计入配额未文档化，列为 M-2 实测项。今天的「约 2 万条天花板」估算（479 B/条 × 10 MB）在 S1 下依然成立，且**本轮 `MAX_PASSWORD_ENTRIES = 2000` 不变**（`utils/storage/vaultCapacity.ts:17`，上限由渲染成本而非存储容量决定）。要突破 2 万条只有 E2（`unlimitedStorage`）一条路，须用户单独拍板，与 E1 无关。

## 五、一致性模型与前置测量

### 5.1 今天靠什么保证一致，S1 之后换成什么

今天两处依赖「一次 `chrome.storage.local.set()` 写多键全成功或全失败」：

- `moveToTrash`（`trashManager.ts:87-91`）：主列表去掉 K 条 + 回收站加上 K 条。
- `restoreFromTrash`（`:146-150`）与 rekey（`changeMasterPassword.ts:150-165`）。

E1 不新增这个依赖，只是让一次 set 的**键数从 2～5 变成 K+1 ～ N+1**。方案分三层，按「能不引入就不引入」排序：

1. **同批写（首选）**：一次 `set` 里同时放条目键与索引键。M-1 已证明「多键 set」在 5000 键量级仍全落无截断（§5.3），**不需要任何额外机制**。
   但 09-25 的 M-5 给这条加了一个必须收窄的前提：**索引键是 88 KB 量级的键，单写 9.8 ms**，每次保存都重写它，等于把 §一 承诺的 150× 压成 14×（同批 11.4 ms @2000）。
   收窄后的规则是——**只在 id 集合真的变化时写索引**：

   | 动作                            | id 集合 | 条目键     | 索引键   | 一致性风险                                                                                                        |
   | ------------------------------- | ------- | ---------- | -------- | ----------------------------------------------------------------------------------------------------------------- |
   | 编辑 / 使用痕迹 / 收藏 / 改标签 | 不变    | 写 K 个    | **不写** | 无——条目已在索引里，写失败就是普通的 `set` reject                                                                 |
   | 新增                            | +1      | 写 1 个    | 同批写   | 索引未落 → 新条目暂不可见，可自愈（重放一次）                                                                     |
   | 删除 / 移入回收站               | −K      | 删/搬 K 个 | 同批写   | 索引未落 → 条目仍"可见"但键已没了，读侧按索引取键会拿到 undefined，必须在读侧计入 `undecryptableCount` 同级的诊断 |
   | 拖拽重编号 / 批量改标签排序     | 可能变  | 写 K 个    | 同批写   | 与今天整包写同风险                                                                                                |

   也就是说：**热路径（编辑保存）根本不碰索引键**，只有增删与排序碰——后者本来就是低频动作，11.4 ms 完全在预算内。

2. **可自愈的顺序写**：仅在 M-1 证明原子性不成立于大键数时启用（M-1 已过线，本条**当前不需要**，保留为 Windows 复跑（M-4）万一翻车时的预案）。顺序为 **先写条目键，后写索引键**；索引键是「可见性开关」——不在索引里的条目键是孤儿，读侧（`getAllPasswords*`）以索引为准，孤儿永不可见。补偿动作放在两个天然存在的空闲点：`getOrWarmCache` 预热成功后、以及 SW 保活闹钟 tick，做一次「扫孤儿 + 扫索引中的缺失键」对账。**不做后台常驻扫描器**，避免新增唤醒成本。
3. **绝不采用的做法**：给每条加 `rev` 做乐观锁并让写失败重试。今天的语义是整包覆盖，引入锁失败会把「保存成功但用户看到报错」变成新的失败模式，属行为变化，需另拍板。

**M-2 配额与字节账 —— 两条页面侧 API 都被证伪，改从磁盘侧取账。**

- `chrome.storage.local.getUsage()` 本机 Chrome 153 **不存在**（探针把错误原文记进 `m2.usageBefore.error`）。
- `navigator.storage.estimate().usage` 在 100→5000 整批写入前后**恒为同一个数**（150,255 B），

  `Local Extension Settings/<extId>`，不在页面 origin 配额下）。因此 §5.2 原写「M-2 用 `estimate()` 实测」的方法**作废**，
  §3.4 那句「Chrome 是否把键名计入配额未文档化」改由磁盘快照回答。
- 替代口径：Node 侧快照该目录字节总和，在「写入 n 个分片键」与「`remove` 掉这批键」之后各取一次。

| N    | JSON 原始体积 B/条 | 目录 写入前 → 写入后 → 清理后 B | 磁盘增量 B/条         | 每键固定开销 |
| ---- | ------------------ | ------------------------------- | --------------------- | ------------ |
| 100  | 449                | 470 → 48,096 → 49,615           | 47,626 = **476.3**    | +27.3        |
| 1000 | 451                | 49,615 → 527,220 → 542,239      | 477,605 = **477.6**   | +26.6        |
| 2000 | 451                | 542,239 → 1,498,515 → 1,528,541 | 956,276 = **478.1**   | +27.1        |
| 5000 | 452                | 1,528,541 → 3,920,866 → 671,768 | 2,392,325 = **478.5** | +26.5        |

- **每键固定开销 ≈ +26～27 B/条（+5.9%），且跨 50× 规模平坦** —— 配额不是分片的瓶颈。
- 5000 键净增 2,392,325 B = 配额 10,485,760 B 的 **22.8%**。
- **夹具键名只有 13 B/条**（`aph_pwd_` + 序号），提案键名 `account_passwords.item_` + 41 字符 id 是 **64 B/条**，
  未量到的 51 B 要 1:1 加进账目 → 真实形态 ≈ **529 B/条**。据此重算算术上限 ≈ **19,800 条**，
  而今天整包口径（479 B/条）≈ 21,900 条 —— 分片把容量天花板压低约 **10%**，属可接受代价，
  **不构成分块（S2）的理由**；`MAX_PASSWORD_ENTRIES = 2000` 由渲染成本而非容量决定，不受影响。
- 清理后目录不回落（+1,519 / +15,019 / +30,026 B）是 leveldb 墓碑与未合并 SST 的常态；
  5000 那一行反而从 3.92 MB 倒降到 672 KB（−856,773 B），是两次快照之间 compaction 跑了一次。
  **两个方向都不是数据丢失信号**，也不要把「清理后仍占 672 KB」读成分片的残留成本。
- 口径局限：整包形态的同一张磁盘表**未测**（磁盘步只写分片键），所以「+26 B/条 = 每键开销」的成立方式
  是「与规模无关、且与既有 479 B/条 估算几乎重合」，不是与整包形态做差得到。

1. **索引键读回不是风险**：88 KB → 1.4～1.9 ms，220 KB → 3.2～3.6 ms，且在 E1 冷读全貌里只占 **约 4%**。

   1.4 / 1.7 ms 同值）。但有一处必须记账的例外：**刚批量写完 n 个分片键之后的那一次单键读普遍偏高**——

   重载会紧接一次读，所以"写后首读"要按尖峰值而不是中位数预算。§6.4 闸 1 的读侧预算因此确认放行，
   B1 接线前不再有未测项。
2. **热读极便宜**：读一条 469 B 条目键 = 0.3～0.4 ms。E1 之后「点开一条详情」这类路径不会变慢。
3. **冷读全库比整包贵 +33%～58%，本稿此前写的「约 16%」偏乐观。** 16% 取自 io 步 @5000 一档
   （175.1 → 202.8），同一批的 @600 与 @2000 其实是 +22% 与 +52% —— 那句话挑了三档里最有利的一档。
   四个格子（SW/options × 2000/5000）的实测总涨幅是 **+33.1% / +38.5% / +44.8% / +57.5%**，
   绝对值 +9.9 / +12.1 / +34.3 / +45.4 ms。
   **原先想把它三段分解（分片形态 / 键名长度 / 索引键）的写法收回**——分解在不同格子互相矛盾，不成立：
   SW 侧分片步 +7.7%→+9.0%、键名步 +19.6%→+30.7%（看着像"大头是键名"），可 options@2000 的分片步是 **+28.3%**
   而键名步只有 **+0.2%**（40.3 → 40.4）。差异的来源是渲染进程那侧还压着整包结构化克隆与主线程成本，
   这 12 ms 无法干净拆给"键名"或"分了键"。因此本稿只保留两条站得住的说法：
   **①总涨幅 +33%～58%；②绝对值 @2000 约 +10～12 ms/次加载。** 而 §5.3-M-5 那侧一次保存省下的是
   **百毫秒量级**，净账成立。**闸 3 已据此改成绝对值口径**（见 §6.4）。
   口径局限：`get` 无「冷/热」开关，重复读同一批键可能命中进程内缓存；SW 侧五样本离散度 <8%，
   options 侧存在 3～6× 的离群首样本（见结论 1），故两上下文中**只采信 SW 的干净配对**做归因，
   options 只用于给"用户实际付的价"定区间。
   另一处不对称：整包读（阶段 B）发生在区域还只有 2 个键时，分片读（阶段 C/D）时区域已有 n+2 个键 ——
   若区域规模会抬高 `get`，这个偏差是**不利于 E1** 的；而 M-6 自己的索引键对照组（1.4 独占 vs 1.5 满区）
   已说明**稳态**区域规模对 `get` 无可测影响（批量写后的首读除外），故该偏差不成立。
   长/短键名两行则完全对称（同一区域、同一批值字节）。

**M-4 Windows 放大倍数 —— 本机不可得，明确不估。**
这台机器只有 macOS。需要 Windows + 杀软真机复跑 `--steps io,audit,disk`。
它只影响收益倍数、不影响方向：分母（`setSmall` 档 0.3～0.8 ms）即使放大 4× 也在 3 ms 内，
而 §2.1 的 <50 ms 线留给 IO 的预算远大于此。风险 5 的等级维持「中」，不因 M-1/M-3 过线而下调。

## 六、迁移设计

### 6.1 迁移的正确性前提

- **迁移不需要明文**：整包数组的元素本身就是自包含密文对象，拆分 = 读旧键 → 逐元素写新键。不派生密钥、不需要主密码、不在内存中持有解密数据。（与 C1 的根本差异；也是它能在锁定态执行的原因。）
- **幂等**：新键以 `id` 命名，重跑同一元素的写入结果一致；迁移可任意时刻中断重放。
- **唯一必须小心的态**：`ensurePasswordsEncryptedAtRest` 的迁移窗口内，整包数组里可能混有**明文**条目（旧版本遗留或写入竞态）。拆分只搬运不改写，明文条目会带着明文落到自己的键里 —— 这与今天整包键里已经有它，**暴露面相同**（同一 `storage.local`、同一 key 空间、同一生命周期），不新增泄露；但必须在 M4 收尾时复用同一套强制加密逻辑扫一遍新键。

### 6.2 五个阶段（每阶段一个可审查、可独立回滚的提交）

| 阶段 | 内容                                                                                                                    | 真值来源 | 回滚方式                       | 出闸条件                                                                            |
| ---- | ----------------------------------------------------------------------------------------------------------------------- | -------- | ------------------------------ | ----------------------------------------------------------------------------------- |

### 6.3 迁移执行细节

- **触发**：SW `onInstalled` / `onStartup` / 首次访问门面时惰性检查 `schemaVersion` 缺失 → 执行。不在 `sidePanel.open()` 手势链上、不在任何渲染热路径上执行。
- **分批让出**：按 200 条一批 `set`，批间 `await new Promise(r => setTimeout(r, 0))`，避免 2000 键一次性写造成长任务（数据层报告 4.2：整库分键重写 90.9 ms @2000，本身可接受，但和序列化、扇出叠在同帧就要让路）。
- **游标**：`account_passwords_migrate` 记录 `{ cursor: id | null, startedAt, done: boolean }`，中断后从游标续；`done` 之前**不允许**切读源。
- **迁移期并发写**：迁移在跑、用户在 options 改了一条 → 迁移结束前**重读旧键做最终对账**，只补「自快照以来 `updateTime` 未变」的条目，其余留给下一次。这与 `ensurePasswordsEncryptedAtRest`（`sessionManager-storage.ts:497-521`）已验证过的写法同构，直接沿用其守卫形态。
- **失败即止**：任一批 `set` reject → 记日志、清 `done`、真值留在旧键、下次再试。迁移永远不允许成为用户可见错误的来源。
- **成本上限**：一次性 ≈ 整包读（43.8）+ 分键全写（90.9）≈ 135 ms IO @2000，分摊在数十个宏任务里。

### 6.4 性能闸（合入 M3 的量化条件）

用同一探针、同一机器、同一夹具复测，与 §4.2 现状对照：

1. `rmw_s1`（读索引 + 写 1 条目键 + 写索引）**P50 < 20 ms**（留 30 ms 给 5 次 AES + 快照重加密，凑满「保存 < 50 ms」）。
2. `shardsAll` 涨幅 ≤ +20% vs `setAll`（最坏情况不倒退）。
3. `getAll_s1`（E1 冷读全貌 = `get(索引)` + 按 id 批量读）**@2000 绝对增量 ≤ 20 ms**（M-6 实测 **+9.9～12.1 ms**：SW 29.9 → 39.8、options 31.4 → 43.5）。
   ~~原口径「涨幅 ≤ +25% vs `getAll`（实测 +16%，约 9 个百分点余量）」**作废**~~：M-6 同窗口配对复测真实键名形态下
   涨幅为 **+33%～58%**（四格 +33.1 / +38.5 / +44.8 / +57.5%），而这条相对线本身没有决策价值——分母（整包冷读）只有
   30 ms，比值随规模单调抬升，且三段分解（分片 / 键名 / 索引）在不同格子互相矛盾（§5.3 M-6 结论 3）。
   **复测时只报绝对毫秒，并同时给出 SW 与 options 两条**；分解值可以采，但只能引 SW 侧（离散度 <8%）。
4. 真机端到端：2000 条库「保存 → 列表出现新行」P50 < 50 ms，用 `benchmarks/measure-options-perf.mjs` 的 CDP `ScriptDuration` 通道取数。
5. 侧边栏秒开 SLA 不退：快照直读路径完全不经分片，必须仍是 < 1 s 无白屏（含 Windows）。

> **闸 1 的两侧都已在 09-25 预检完（M-5 写 / M-6 读，@2000）**：写侧 1 条目键 0.3～0.7 ms、写索引键 8.7～9.8 ms、
> 两者同批 8.6～11.4 ms；读侧单键 `get` 一个 88,036 B 索引对象 **1.4～1.9 ms**，稳态下区域里已有 2000 个分片键时
> 读数不变（1.5 / 1.9）——但**批量写完之后的那一次读除外**（首样本 9.9 ms @options2000 / 20.6 ms @options5000，
> 见 §5.3 M-6 结论 1），所以「保存后紧接全库读」这条路径要按尖峰值预算。只要按 §5.1 把索引写收窄到「id 集合变化」，
> **编辑保存这一档离 20 ms 线很远**，新增/删除这一档留约 8 ms 余量；读侧的索引键只占 E1 冷读全貌的约 **4%**。
