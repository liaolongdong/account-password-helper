## 一、结论先行

1. **E1 是当前实测到的最大单项杠杆，但它只治写侧。** 保存 1 条的 IO 全貌（`rmw`）在 2000 条时为 **263.1 ms**、5000 条时 **941.8 ms**；分键后同等动作落在 `setSmall` 档：**0.8 ms / 1.6 ms**（约 **150×**）。首屏侧 E1 不但没有收益，全库读还贵约 **16%**（66.7 vs 43.8 ms @2000）——首屏 < 1s 由分页（已落地）与快照/SW 缓存承担，**不要把它记在 E1 账上**。
2. **E1 的迁移不需要解密、不改变密文格式。** 一条 `EncryptedPasswordEntry` 是自包含对象（`utils/encryption.ts:263-285` 按字段加密，`id`/`order`/`tag`/时间戳本就是明文），把「一个 N 元素数组」改成「N 个键各存一个元素」是**纯结构搬运**：不派生密钥、不触碰 AES、不动 `.aph` 备份格式。这是 E1 与 C1/C2（at-rest 密文格式）最本质的区别，也是它可以「双写 + 对账 + 可回滚」的原因。
3. **E1 的真实代价不是性能，是三件事**：① 跨键一致性（今天靠「一次 `set` 写 2～5 个键」的原子性保证，见 `trashManager.ts:88-91`、`changeMasterPassword.ts:154-165`）；② **扇出语义重写**（三个上下文的 `onChanged` 快路径全部假设 `changes[account_passwords].newValue` 是整包数组）；③ 未验证的**键数上限与部分失败语义**。
4. **本稿推荐落点：主库按条目分键 + 单独索引键，回收站/历史/身份/快照四处本轮不动**（对应数据层报告第八节第 2 条的选项 (b)）。理由见第四节末。
5. **落地前必须先跑完第五节的 4 个前置测量**，其中「一次 `set` 写 2000 个键」这一项若结果为「截断」或「部分成功且不报错」，**本方案直接否决**，退回 chunk 形态重测。

## 二、要解决的问题与验收口径

### 2.1 问题定义（用户视角）

| 动作                         | 今天（2000 条，实测/推算分段）                                    | 阈值         | 谁负责达标                                |
| ---------------------------- | ----------------------------------------------------------------- | ------------ | ----------------------------------------- |
| 打开管理页                   | 全库读 43.8 + 全库解密 410.6 + 分页后只渲染 100 行                | **< 1 s**    | 分页（已落地）+ P0-1/P0-3，**不是 E1**    |
| 添加 / 保存 1 条             | `rmw` 263.1 IO + 5 次 AES ≈ 2 ms + 快照重加密 3.9 + 扇出 211～245 | **< 50 ms**  | **只有 E1**（P0/P1 都碰不到 IO 与投递段） |
| 过滤 / 搜索 / 排序           | 命中集计算实测个位数毫秒（渲染层报告 3.1），渲染受分页保护        | 无可感知停顿 | 分页 + `keywordMatch`，与 E1 无关         |
| 批量改标签 / 收藏 / 使用痕迹 | 一次整包写 + 一次整包载荷投递；P0-3 后外部写入侧可零解密就地修补  | 无可感知停顿 | P0-2/P0-3 已吃大头，E1 吃剩下那笔整包写   |
| 导出 / 备份                  | 读整库解密（410.6）+ 内存组装，无写放大                           | 无可感知停顿 | 与 E1 无关                                |

**一句话验收**：E1 若落地，唯一必须被它拿下的指标是「保存/新增 1 条在 2000 条库上 P50 < 50 ms」。其余指标 E1 只允许**不倒退**（全库读涨幅 ≤ 25%、整库重写涨幅 ≤ +20%、首屏仍 < 1 s）。

### 2.2 硬约束（来自 `agents.md`，不可协商）

- 不改 `.aph` 备份/导出格式，不改导入模板，不改加密算法、KDF 参数、密文编码 —— E1 只改**「一个逻辑集合摊到几个 storage 键上」**。
- 迁移必须保留旧数据可读、必须有回滚路径，并且**成功 / 失败 / 旧格式 / 边界**四类测试齐备（第七节矩阵）。
- `storage.local` 中任何时刻不得出现比今天更多的明文（第十节风险 3 专门处理迁移窗口的双写副本）。
- 不与 P0 混在一个提交批次；E1 自身按第五节批次拆分。

## 三、键结构选型

### 3.1 三个候选形态

单位 ms，取自数据层报告 4.2 的 options 侧实测（600 / 2000 / 5000）。

| 形态                        | 一次 set 的键数 | 保存 1 条写成本  | 全库读         | 整库重写     | 主要风险                                     |
| --------------------------- | --------------- | ---------------- | -------------- | ------------ | -------------------------------------------- |
| **S0 现状**（单键整包）     | 1               | 63.7 / 245.9     | 43.8 / 175.1   | 63.7 / 245.9 | 无                                           |
| **S1 每条一键**（本稿推荐） | 1 + 索引        | **0.8 / 1.6**    | 66.7 / 202.8   | 90.9 / 240.0 | 键数上限未验证；扇出改动最大                 |
| **S2 每 200 条一块**        | 1 + ⌈N/200⌉     | 未实测（~96 KB） | 未实测（≈ S0） | ≈ S0         | 块内丢更新窗口大于 S1；收益只有 S0→S1 的中间 |

`shardsAll`（整库按条目分键重写）2000 条时 90.9 vs 整包 63.7 —— 这是**改主密码 / 恢复备份 / 全量导入 / 拖拽重编号**的最坏情况，涨幅 +43%；数据层报告在 5000 条口径下给出的对照是 240.0 vs 245.9（基本等价）。两个规模结论一致：**最坏情况不进质量级，仍在线性可接受区间**。

### 3.2 为什么选 S1 而不是 S2

S2 的收益是「写放大 ÷ 200」，但它的**语义复杂度与 S1 完全一样**（索引、跨键一致性、扇出改写、迁移，一个都不能少），却拿不到 S1 的「`changes` 只含被改条目 → 各上下文天然知道哪一条变了」这条结构性红利（数据层报告第七节 P2 段：这条红利正是 P1「变更票据」想要而拿不到的性质）。既然复杂度同价，取收益上界。

### 3.3 具体键名（提案）

```text
account_passwords_index      → { v: 1, ids: string[], count: number, rev: number, migratedAt?: number }
account_passwords.item_<id>  → 单个 EncryptedPasswordEntry 对象（结构与今天数组元素完全一致）
```

设计要点：

- **元素结构零改动**：`{...entry, username: <cipher>, ..., encrypted: true}` 原样搬到键值，不做字段重排、不加包装数组。这让「读一个键 → 解一个条目」与今天的「读整包 → 解第 i 个元素」逐位等价，现有 `decryptPasswordEntry` 与 `undecryptableCount` 语义原样保留。
- **`id` 进键名**：`chrome.storage.local.get(key)` 按 key 取，单条读不必扫描全库；这也是 `updatePassword(id)` / `updatePasswordInSession(id)` 从现在起不必再读整包的原因。
- **索引键必选**：`get()` 无参虽可取全部，但会把回收站/历史/身份/提醒一起拉进来；`getKeysByFilter` 在 MV3 已不推荐。索引键体积要按真实 id 形态算：`generateId()` 产出 `'uuid-' + UUID` 即 **41 字符**（`utils/generateId.ts:10-15`），2000 条的 JSON 数组约 **88 KB**。它是「比条目键大两个数量级的小键」，写成本落在 `setSmall` 0.8 ms 与 `setAll` 63.7 ms 之间、**未实测**（M-2 覆盖），且增删改一条时**必须与条目键同批写**（一致性方案见第五节）。
- **`rev` 只做诊断，不做锁**：每次结构变更 +1，用于对账与「迁移后校验」，不引入乐观并发失败路径（今天整包写同样是 last-write-wins，S1 不比它更弱）。
- **不引入 `account_passwords` 之外的新权限、不改 `permissions`/`host_permissions`。**

### 3.4 配额口径（必须写清，避免被当成"存不下"的解药）

`chrome.storage.local` 配额是**总量**口径：探针运行时读到 `local`/`session` 各 10,485,760 字节、`hasUnlimitedStorage: false`（数据层报告第十节第 3 条）。分片**不提高总量上限**，且键名与索引本身要计字节：键名 `account_passwords.item_` + 41 字符 id ≈ 64 B，2000 个约 **128 KB**，再加 88 KB 索引键 —— 相对 10 MB 是 2% 量级，**可接受但不是零**，且 Chrome 是否把键名计入配额未文档化，列为 M-2 实测项。今天的「约 2 万条天花板」估算（479 B/条 × 10 MB）在 S1 下依然成立，且**本轮 `MAX_PASSWORD_ENTRIES = 2000` 不变**（`utils/storage/vaultCapacity.ts:17`，上限由渲染成本而非存储容量决定）。要突破 2 万条只有 E2（`unlimitedStorage`）一条路，须用户单独拍板，与 E1 无关。

### 4.1 前置修正（与 E1 无关、但 E1 依赖它）

`composables/useSidepanelData.ts:583,601` 直接写死字符串 `'account_passwords'` 而不是 `STORAGE_KEYS.PASSWORDS`。E1 之后侧栏 watcher 必须按前缀匹配键名，**这两处若不同时改，会静默失效**（`changes['account_passwords']` 永远不存在 → 侧栏不再响应外部写入，表现为「另一个页面改了数据这边不刷新」）。这是一次独立、零行为变化的修正，应在 E1 之前单独提交。

### 4.2 本轮刻意不动的四处

| 面                     | 键                        | 不动的理由                                                      |

| 回收站                 | `account_passwords_trash` | 30 天 TTL、体量上限 = 主库的零头；分片要连带重设计 4 个批量操作 |

## 五、一致性模型与前置测量

### 5.1 今天靠什么保证一致，S1 之后换成什么

今天两处依赖「一次 `chrome.storage.local.set()` 写多键全成功或全失败」：

- `moveToTrash`（`trashManager.ts:87-91`）：主列表去掉 K 条 + 回收站加上 K 条。
- `restoreFromTrash`（`:146-150`）与 rekey（`changeMasterPassword.ts:150-165`）。

E1 不新增这个依赖，只是让一次 set 的**键数从 2～5 变成 K+1 ～ N+1**。方案分三层，按「能不引入就不引入」排序：

1. **同批写（首选）**：一次 `set` 里同时放条目键与索引键。若第 5.2 节 M-1 测量证明「多键 set 原子」在 2000 键量级仍成立，**不需要任何额外机制**。
2. **可自愈的顺序写**：仅在 M-1 证明原子性不成立于大键数时启用。顺序为 **先写条目键，后写索引键**；索引键是「可见性开关」——不在索引里的条目键是孤儿，读侧（`getAllPasswords*`）以索引为准，孤儿永不可见。补偿动作放在两个天然存在的空闲点：`getOrWarmCache` 预热成功后、以及 SW 保活闹钟 tick，做一次「扫孤儿 + 扫索引中的缺失键」对账。**不做后台常驻扫描器**，避免新增唤醒成本。
3. **绝不采用的做法**：给每条加 `rev` 做乐观锁并让写失败重试。今天的语义是整包覆盖，引入锁失败会把「保存成功但用户看到报错」变成新的失败模式，属行为变化，需另拍板。

## 六、迁移设计

### 6.1 迁移的正确性前提

- **迁移不需要明文**：整包数组的元素本身就是自包含密文对象，拆分 = 读旧键 → 逐元素写新键。不派生密钥、不需要主密码、不在内存中持有解密数据。（与 C1 的根本差异；也是它能在锁定态执行的原因。）
- **幂等**：新键以 `id` 命名，重跑同一元素的写入结果一致；迁移可任意时刻中断重放。
- **唯一必须小心的态**：`ensurePasswordsEncryptedAtRest` 的迁移窗口内，整包数组里可能混有**明文**条目（旧版本遗留或写入竞态）。拆分只搬运不改写，明文条目会带着明文落到自己的键里 —— 这与今天整包键里已经有它，**暴露面相同**（同一 `storage.local`、同一 key 空间、同一生命周期），不新增泄露；但必须在 M4 收尾时复用同一套强制加密逻辑扫一遍新键。

### 6.2 五个阶段（每阶段一个可审查、可独立回滚的提交）

| 阶段 | 内容                                                                                                                    | 真值来源 | 回滚方式                       | 出闸条件                                                                            |
| ---- | ----------------------------------------------------------------------------------------------------------------------- | -------- | ------------------------------ | ----------------------------------------------------------------------------------- |

### 6.3 迁移执行细节

- **触发**：SW `onInstalled` / `onStartup` / 首次访问门面时惰性检查 `schemaVersion` 缺失 → 执行。不在 `sidePanel.open()` 手势链上、不在任何渲染热路径上执行。
- **分批让出**：按 200 条一批 `set`，批间 `await new Promise(r => setTimeout(r, 0))`，避免 2000 键一次性写造成长任务（数据层报告 4.2：整库分键重写 90.9 ms @2000，本身可接受，但和序列化、扇出叠在同帧就要让路）。
- **游标**：`account_passwords_migrate` 记录 `{ cursor: id | null, startedAt, done: boolean }`，中断后从游标续；`done` 之前**不允许**切读源。
- **迁移期并发写**：迁移在跑、用户在 options 改了一条 → 迁移结束前**重读旧键做最终对账**，只补「自快照以来 `updateTime` 未变」的条目，其余留给下一次。这与 `ensurePasswordsEncryptedAtRest`（`sessionManager-storage.ts:497-521`）已验证过的写法同构，直接沿用其守卫形态。
- **失败即止**：任一批 `set` reject → 记日志、清 `done`、真值留在旧键、下次再试。迁移永远不允许成为用户可见错误的来源。
- **成本上限**：一次性 ≈ 整包读（43.8）+ 分键全写（90.9）≈ 135 ms IO @2000，分摊在数十个宏任务里。

### 6.4 性能闸（合入 M3 的量化条件）

用同一探针、同一机器、同一夹具复测，与 §4.2 现状对照：

1. `rmw_s1`（读索引 + 写 1 条目键 + 写索引）**P50 < 20 ms**（留 30 ms 给 5 次 AES + 快照重加密，凑满「保存 < 50 ms」）。
2. `shardsAll` 涨幅 ≤ +20% vs `setAll`（最坏情况不倒退）。
3. `getAll_s1` 涨幅 ≤ +25% vs `getAll`（数据层报告实测 +16%，有约 9 个百分点余量）。
4. 真机端到端：2000 条库「保存 → 列表出现新行」P50 < 50 ms，用 `benchmarks/measure-options-perf.mjs` 的 CDP `ScriptDuration` 通道取数。
5. 侧边栏秒开 SLA 不退：快照直读路径完全不经分片，必须仍是 < 1 s 无白屏（含 Windows）。
