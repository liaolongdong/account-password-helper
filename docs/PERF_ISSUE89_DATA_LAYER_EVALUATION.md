## 一、结论先行

1. **分页只能治 issue 里的一半症状，而那一半已经治过了。** 用户标题说的"保存约 600 条后点新增异常卡顿"
   属渲染层，P1 落地后同一时间窗真机对比 `save` 的渲染进程脚本时长 6.419 s → 0.221 s。剩下那些抱怨——
   打开管理页转圈、批量导入慢、改主密码长时间无反馈、一次删一批卡住、Windows 上格外明显——
   **分页一秒都治不到**：它们的成本全在「整包重写 + 广播重复投递 + 三个入口各解密一遍（每次 5N 次 AES 调用）」上，
   跟屏幕上显示多少行无关。

2. **一次"保存"的大头是整包重写 + 广播投递，加解密只占零头（真机实测）。** 4.2 表：把 1 条改动落盘
   （读整包 + 改 1 条 + 写整包，**不含任何加解密与渲染**）在 600 / 2000 / 5000 条上各要
   **66.8 / 263.1 / 941.8 ms**；而 `storage.onChanged` 从 `set` 发出到上下文收到回调又要
   **43～55 / 211～245 / 538～852 ms**。那条路径上扩展自己付的 5 次 AES 约 **2 ms**。
   也就是说：**在发起保存的那个上下文里，"把这条数据落盘并让别的上下文知道"比"把它加密"贵 30～800 倍。**
   若按最坏情形把三个上下文各解一遍也算进来（第四节），加解密总量仍可能是最大一项——但那一块
   **不需要改存储结构就能拿掉**（D3/D5），而整包重写与全量载荷**只有改写结构才能拿掉**。
   所以排序是：先做不需要点头的（削解密重复），再拍板要不要做写结构，视图层排最后。

3. **加密本身不是瓶颈，"调用次数"才是。** 实测同机同进程：1.45 MB 整包 AES-GCM 加密 **2.7 ms**；
   而 5000 条 × 5 字段的解密 **732 ms**。数据量完全相同，差 **约 270 倍**，差值全是每次
   `crypto.subtle` 调用的固定开销（Promise 调度 + 参数封送 + IV/缓冲分配）。
   所以"减少加解密开销"的正确含义是**减少调用次数**，不是换算法、更不是降 PBKDF2 迭代（后者只发生在
   解锁/改密，且降它属于安全退化）。

4. **零格式改造里性价比最高的是 Base64 助手**。现口径解码
   （`utils/encryption.ts:197` `Uint8Array.from(atob(s), c => c.charCodeAt(0))`）在**同一次迭代内配对**测得：
   1 MB 解码 **545.5 / 170.0 / 143.9 ms → 分块 for 的 7.5 / 6.1 / 5.2 ms**（**20～70×**）；
   3 万次小字段解码 **170.7～324.9 ms → 9.9～17.0 ms**。
   这条改动**不动存储格式、不动密文、不动任何接口签名**，密文字节逐字不变（bench 里有 `b64Match` 断言）。
   但按第 2 条的比例，它属于"把零头再削掉一截"——值得做，不是决定性的。

5. **格式改造要分成两类来看，它们的收益差一个数量级。**
   - **加密格式（C1/C2）**：把"每条 5 字段 5 次调用"收成"每条 1 次调用"实测 5000 条解密
     732 → 322 ms（2.3×）；"全库 1 次调用"（快照与 `.aph` 备份已在用的形态）实测 5000 条 218.7 ms，
     其中 AES 只占 2.7 ms、余下几乎全是慢 base64 与解析，**换快助手后推算约 20～25 ms**（未实测）。
     对照第 2 条，这治的是零头，**优先级低于写结构**。
   - **存储结构（E1 分键/分片）**：单条保存 245.9 → **1.6 ms**（约 **150×**），最担心的整库重写场景
     240.0 vs 245.9 ms **几乎等价**（不倒退），冷读全库则要贵 **+33%～58%**（09-25 由 E1 设计稿 §5.3 的 M-6
     同窗口配对复测更正，四格 +33.1/+38.5/+44.8/+57.5%、绝对值 @2000 只多 9.9～12.1 ms；本小节原先写的"只贵约 16%"
     取自 @5000 一档的短键名测量，同批 @600/@2000 实为 +22%/+52%，那句话挑了最有利的一档），还顺带把 `onChanged` 的载荷
     从"2.4 MB × 每上下文一次结构化克隆"降到"500 B × 变更条数"。
     **这是当前实测到的最大数量级杠杆**——我在写探针时曾按保守估计认为它"上限收益必然薄"，
     实测把这个判断推翻了（详见 4.2）。
     **但风险等级不因数字变好而下降**：它仍是 at-rest 存储结构改造（迁移 + 索引键 + 跨键一致性），
     且**不解决配额**；今天的一致性靠单键原子写保证。属于必须用户点头才动的类别。

6. **存在一条谁也绕不过去的硬上限，且它比"卡"更严重。** 探针在真机运行时读到
   `chrome.storage.local.QUOTA_BYTES = 10,485,760`（10 MB）、`storage.session` 同为 10 MB、
   `storage.sync` 102,400，`hasUnlimitedStorage: false`（manifest 未声明，`wxt.config.ts:93-108` 权限清单已核对）。
   实测每条目 at-rest 约 **479 B**，即 **约 2 万条封顶**——而回收站（`password_trash`）、密码历史
   （`password_history`）、身份信息库共用同一个 10 MB，实际可用条目数更低。到量之后的表现不是变慢，
   是 `chrome.storage.local.set()` 失败 = **保存丢数据**。issue 里"用户 600 条就卡"离这堵墙很远，
   但"彻底解决大 Vault"这个词如果不提它，报告就不诚实。

## 三、数据层成本曲线（实测）

### 3.1 体积：一切成本的乘数

| 指标                                     | N=600  | N=2000 | N=5000  |
| ---------------------------------------- | ------ | ------ | ------- |
| 每条目 at-rest 字节                      | 479.0  | 479.4  | 479.7   |
| 整包密文 JSON（= 一次写入的量）          | 287 KB | 959 KB | 2.40 MB |
| 全库明文 JSON（= 快照/备份的加密前体积） | 174 KB | 580 KB | 1.45 MB |
| 整包单密文（base64，= 快照形态体积）     | 232 KB | 773 KB | 1.94 MB |

> 注：另一份报告 3.2 节把 600 条整包估成"180～240 KB（算术推算未实测）"，实测 **287 KB**，
> 低估约 20～60%。写放大相关结论应按 287 KB 起算。

### 3.2 全库解密（打开管理页 / SW 冷缓存预热 / 侧栏重载同一条路径）

| 形态                                                                    | 600   | 2000  | 5000  | 说明                                                                                                                                          |
| ----------------------------------------------------------------------- | ----- | ----- | ----- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| **现口径**：条目间 `Promise.allSettled` 并行，条目内 5 字段串行 `await` | 100.2 | 410.6 | 732.0 | `passwordCrud.ts:449-497` + `encryption.ts:273-277`                                                                                           |
| 变体 A：字段级也并行（**格式不变**）                                    | 87.0  | 322.6 | 725.3 | 大 N 下**无收益**，且并发 5N 个 subtle 任务反而更抖 → **否决**                                                                                |
| 变体 B：整条目一次 AES（**需改 at-rest 格式**）                         | 48.9  | 115.8 | 321.9 | 2.05× / 3.55× / 2.28×，密文体积 −16%                                                                                                          |
| 变体 C：全库一次 AES（快照/`.aph` 备份**已经在用**的形态）              | 32.4  | 116.5 | 218.7 | 由 `snapshotDecrypt + snapshotParse` 直读；绝对值与 3.4 的解码行数一致，说明**大头在慢 base64 而不是 AES**（AES 1.45 MB 只要 2.7 ms，3.5 表） |

### 3.3 整库重加密（改主密码 / 恢复备份 / 批量导入）

| 形态                                      | 600   | 2000  | 5000   |
| ----------------------------------------- | ----- | ----- | ------ |
| 现口径：`for…await` 逐条、每条 5 字段串行 | 216.2 | 705.0 | 1295.0 |
| 条目级并行 `Promise.all`（**格式不变**）  | 117.0 | 396.3 | 741.7  |

→ 约 **1.8×**，零格式改造、零行为变化。改主密码是全串行链路里最容易拿的一半收益。

### 3.4 序列化 / 快照 / Base64

| 项                                                         | 600           | 2000         | 5000        |
| ---------------------------------------------------------- | ------------- | ------------ | ----------- |
| `JSON.parse` 整包密文                                      | 1.2           | 4.0          | 8.3         |
| `JSON.stringify` 整包                                      | 1.7           | 4.7          | 9.5         |
| 快照加密（stringify + TextEncoder + 1 次 AES + 慢 base64） | 30.1          | 151.7        | 264.5       |
| 快照解密 + parse                                           | 32.4          | 116.5        | 218.7       |
| base64 **解码** 1 MB：现口径 / 分块 for                    | 545.5 / 7.5   | 170.0 / 6.1  | 143.9 / 5.2 |
| base64 **编码** 1 MB：现口径 / 分块                        | 147.3 / 149.3 | 145.2 / 97.5 | 89.3 / 82.2 |
| base64 解码 3 万次小字段：现口径 / 分块 for                | 324.9 / 13.4  | 222.2 / 17.0 | 170.7 / 9.9 |
| 每次解密多余的一对 `slice`（3 万次）                       | 5.6           | 8.5          | 4.7         |

**三条判读**：

- **序列化不是瓶颈**（parse+stringify 合计 <20 ms @5000）。任何"为了少 stringify 而改存储结构"的提议
  收益上限只有几毫秒，可以直接排除。
- **base64 解码是加解密链路里被低估的最大单项**。同一迭代内配对：1 MB 解码 **545.5 / 170.0 / 143.9 ms
  → 5.2 / 6.1 / 7.5 ms**，3 万次小字段 **170.7～324.9 ms → 9.9～17.0 ms**。
  而它藏在**每一条解密的必经路径**上（`decryptData` → `atob` → `Uint8Array.from`）。
  换成 for 循环填充即可拿掉 90% 以上；这是"零格式改造"里唯一真正的数量级收益。
  **口径提醒**：现口径的三列绝对值彼此差 3～4 倍（545 vs 144），是 warmup 顺序 + GC 抖动，
  所以这条只认**同迭代配对的倍数**，不认跨列绝对值；2 MB 级别的耗时只在原语脚本 stdout 里出现过、
  未落进 JSON，故本表一律用 1 MB 口径。
- **base64 编码没有等价收益**（现口径 89～149 ms/MB，分块 82～149 ms）。
  结论：**编码侧不动，解码侧必动**。

### 3.5 密码学原语单项（用于判断"什么不能动"）

| 原语                                          | 实测                                      | 用在哪                                                                                                                                      |
| --------------------------------------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| PBKDF2-SHA256 **600,000** 次迭代（32 B 输出） | **433 ms**（三次 433.8 / 431.7 / 433.5）  | 仅 `createSession` / `deriveEncryptionKey` / `deriveVerifierHash`（`encryption.ts:111,131`），CRUD 走三级缓存的数据密钥，**不在保存路径上** |
| AES-GCM 加密 1.45 MB 整包                     | **2.7 ms**                                | 快照/备份形态                                                                                                                               |
| AES-GCM 单次小字段（≤120 B）                  | 约 **25～30 µs**（732 ms ÷ 25000 次反推） | 现口径 at-rest，5N 次                                                                                                                       |

> **口径说明**：本节三行来自一次性原语脚本（`crypto.subtle` 直调，结果打印在终端、未写入 JSON 产物），
> 复现方式见附录 A 的说明；第三行是**反推值**（732 ms ÷ 25 000 次），不是独立计时。
> 表里唯一有 JSON 背书的是 `decryptAllCurrentMs`（732 ms）与 `packedEncryptAllMs`。
> 因此本节只用于回答"AES 吞吐是不是瓶颈 / PBKDF2 能不能动"这类量级判断，不作为单项优化目标。
>
> **两处需要澄清的既有数字**：另一份报告 3.2 节写"单次 PBKDF2 派生实测 1.6～2.5 秒"，
> 与本次直调的 433 ms 差 4～6 倍。差异来源应是它引的 `tests/utils/encryption.test.ts` 口径
> （该文件整跑 4.6 s，含约 10 次派生 ≈ 每次 450 ms，与本次吻合）。
> **报告结论不受影响**（无论 0.43 s 还是 1.6 s，PBKDF2 都不在保存路径上），但下次引用请写"单次派生约 0.43 s（Node 直调），改主密码要付两次"。

## 四、一次"保存"到底付了几次全量解密（跨入口扇出）

```
用户在管理页改 1 条密码字段
  └─ options: updatePassword → 1 次读整包 + 5 次 AES（这 1 条）+ 1 次整包写   ← 便宜，P1 之后已就地更新 Vue 状态
       │      （passwordCrud.ts:164-213；元数据类改动走 :180-184 就地分支，零加解密）
       └─ chrome.storage.onChanged 广播到 4 个上下文
            ├─ SW   ：命中 metadata 标记 → applyMetadataOnlyUpdate（就地补 + **仍整包重加密快照**）
            │         未命中 → invalidatePasswordCache + warmPasswordCache = **5N 次解密** + 快照 stringify + AES + base64 编码 + session 写
            │         （backgroundServices.ts:670-706 → passwordCache.ts:342-409,127-154）
            ├─ options：useStorageWatcher → onPasswordDataChange = loadPasswords = **5N 次解密** + 整表重渲染
            │         （App.vue:1132-1139；本地写入由 skipIf 守卫吞掉一次，外部写入不吞）
            └─ 侧栏  ：命中 metadata → applyMetadataOnlyPatch（**零解密**）
                      未命中 → loadPasswords = **5N 次解密**（useSidepanelData.ts:583-617，锁定时整支不执行）
```

一次「内容字段」保存，最坏情形下**同一批数据被完整解密三遍**（SW / options / 侧栏），
外加一次整包重加密的快照。按 3.2 表现口径估：N=600 约 300 ms、N=2000 约 1.2 s、N=5000 约 2.2 s
的纯解密工作量，分散在三个进程/文档里，其中两处在主线程。

**再叠上 4.2 的 IO 与投递账**（同一用户动作，600 / 2000 / 5000 条）：
写入侧 `rmw` 66.8 / 263.1 / 941.8 ms，广播落地 `onChanged` 43～55 / 211～245 / 538～852 ms，
加解密侧最坏 3×5N 约 300 / 1200 / 2200 ms 且分散在三个上下文。
**三段里最长的那条不是加解密，是"整包重写 + 全量载荷的跨上下文投递"**——这决定了 E1（改写结构）
和 D5（改载荷）的收益量级高于 D1/D2（改加解密）。

（渲染层那份报告 9.4/9.5 已经用真机 CDP `ScriptDuration` 坐实过：P1 之前"一次保存 = 整表重排"，
落地后 `save` 场景 6.419 s → 0.221 s。**上面这张图表的是 P1 之后仍然存在的剩余成本**。）

### 4.1 两个已经不对称、可以低成本补齐的缺口

1. **options 侧没有元数据就地修补。** 侧栏有 `isMetadataOnlyChange` + `applyMetadataOnlyPatch`
   （`useSidepanelData.ts:601-615`、`:630-647`），SW 有 `applyMetadataOnlyUpdate`
   （`passwordCache.ts:203-246`），**只有 options 的 watcher 是"要么守卫吞掉、要么全量重载"**
   （`useStorageWatcher.ts:70-79`）。收藏/使用痕迹/排序这类外部写入在管理页里会白付一次 5N 解密
   加一次整表重排。补法是把侧栏那对现成函数接上（同一判据、同一白名单），**不改交互、不改数据**。
2. **回收站四处按 id 串行读写提醒表。** `moveToTrash:94`、`permanentDeleteFromTrash:174`、
   `emptyTrash:198`、`cleanExpiredTrash:238` 都是 `for (const id of ids) await removeReminder(id)`，
   而 `removeReminder`（`reminderManager.ts:92-99`）每次**读整包 `password_reminders`**、命中才写。
   删 100 条 = 100 次串行 storage 往返。旁边 `cleanOrphanReminders:133-148` 已经是
   "一次读 → 内存过滤 → 最多一次写"的正确形态，照它加个 `removeReminders(ids: string[])` 即可，
   行为等价（写次数从 ≤M 次变 1 次，读次数从 M 次变 1 次）。
   这条是**缺陷修复量级**的免费收益，和分页/格式改造完全无关。

### 4.2 真机 storage IO（`chrome.storage.local` 到底值多少毫秒）

> 每动作 5 次取中位数；夹具写在 `bench_blob` 而非 `account_passwords`，以免扩展自身的扇出（SW 重预热、
> 侧栏重载）混进 IO 计时。原始数据 `benchmarks/results/storage-io-io3.json`。
> **本节是整份报告里权重最高的一张表**——它把"保存 1 条"从模糊的"感觉卡"变成了可分解的毫秒。

单位 ms，`600 / 2000 / 5000` 条目。表内是 **options 页面**（用户实际付的价），Service Worker 同口径数字列在表后。

| 动作（含义）                                                                   | 600        | 2000         | 5000             |
| ------------------------------------------------------------------------------ | ---------- | ------------ | ---------------- |
| `setAll` 整包写（现状：保存 1 条要把 N 条重写一遍）                            | **16.7**   | **63.7**     | **245.9**        |
| `getAll` 整包读                                                                | 10.9       | 43.8         | 175.1            |

Service Worker 侧同口径：`setAll` 26.5 / 98.8 / 217.8，`getAll` 12.3 / 54.2 / 143.2，

（SW 在 IO 上与渲染进程基本同价，个别项略高——**"放到后台进程"不会让整包重写变便宜**。）

**这张表改写了两个此前的判断：**

1. **"保存 1 条"的主成本是整包重写，而且它比分页能省的东西贵得多。** `rmw` 是**纯 IO 地板价**：
   不含任何加解密（那 5 次 AES 约 2 ms）、不含快照重加密、不含渲染。5000 条时一次保存
   光读写就要 **约 0.94 秒**，再叠加上表的 `onChanged` 投递 **0.5～0.9 秒**才落到各上下文。
   用户感知的"保存后一顿"里，**这两段是只有改存储结构才能拿掉的部分**，也是分页完全碰不到的部分
   （三遍全量解密另算，见第四节；那一块能靠 D3/D5 拿掉）。
2. **分键/分片（E1）的收益上限不是"薄"，而是当前最大的数量级杠杆。** 我在写探针时曾把
   `setSmall` 当作"上限收益必然有限"的保守估计（脚本头注释原话），实测把它推翻了：
   - 单条保存：245.9 → **1.6 ms**（约 **150×**）；
   - 最担心的"整库重写"（改主密码 / 恢复备份 / 导入 / 拖拽重编号）：分键 240.0 ms vs 整包 245.9 ms ——
     **几乎等价**，最坏情况不倒退；
   - 全库读：分键 202.8 vs 整包 175.1 ms —— **本档 +16%，但它是三档里最低的**（@600 +22%、@2000 +52%）。
     09-25 M-6 用真实 49 B 键名同窗口配对复测，冷读全貌涨幅为 **+33%～58%**（四格 +33.1/+38.5/+44.8/+57.5%），
     绝对值 @2000 只多 **9.9～12.1 ms**；
     且读侧本来就被 `storage.session` 快照（写 23.5 ms）与 SW 内存缓存挡在前面。
   - 附带把 `onChanged` 的载荷从"整包 2.4 MB × 每个上下文一次结构化克隆"降到"500 B × 变更条数"。
     载荷既然变小，第四、五节里那笔**投递成本**必然跟着降；但**小载荷的实际投递延迟本次未测**
     （探针的 `onChanged` 用的是整包载荷），所以这里只给方向不给数字。
     更强的那条理由是**语义层面**的：分键后 `changes` 只含被改的键，各上下文天然知道"哪一条变了"，
     扇出的三遍全量解密可以退化成一次就地补 1 条（详见第七节 P2 与 P1 的关系）。
     **但**：E1 仍是存储结构改造（迁移 + 索引键 + 一致性），风险等级不因数字变好而自动下降——
     只是"值不值得冒这个风险"的答案从"不确定"变成了"值得认真讨论"。

**两个必须如实标注的边界**：

- `chrome.storage.local.set` 的多键写入是否原子，是今天 `moveToTrash`（`trashManager.ts:87-90` 一次 set 同写
  passwords + trash）和 rekey（`changeMasterPassword.ts:154` 一次 set 同写 4 个键 + 会话键）**已经在依赖**的性质。
  E1 不新增这个依赖，只是将键数变多；**键数上限与部分失败语义需要专项验证**（见第十节）。
- 本机为 macOS + SSD，**Windows + 杀软扫描下这些数字会放大**（项目既有结论：2～4×），
  即整包写的代价在 issue 用户最可能所处的环境里更贵，而 500 B 小键写入受扫描影响小得多。
  这条放大关系**未实测**，只是外推。

### 5.1 为什么"分页"不是这个问题的最优解（定量版）

分页改变的是**「屏幕上同时存在多少行 DOM」**，而 issue 里大 Vault 的成本分布是：

- 全库解密：`5N` 次 AES 调用（3.2 表）。分页后 `passwords.value` 仍是全量，**一次都不省**。
- 写放大：每次保存重写 287 KB（600 条）～2.40 MB（5000 条），实测 `rmw` **66.8 / 263.1 / 941.8 ms**
  （4.2，纯 IO、不含加解密与渲染）。与视图无关，**一点不省**。
- 广播投递：`onChanged` 落地 **43～55 / 211～245 / 538～852 ms**，且载荷是整包。与视图无关，**一点不省**。
- 扇出：一次保存三处各解密一遍。与视图无关，**一点不省**。
- 配额：10 MB / 约 2 万条（运行时 `QUOTA_BYTES` 已读）。与视图无关，**一点不省**。
- 计算（过滤 + 排序 + 拼音匹配）：渲染层报告 3.1 实测 500 条 1.23 ms、2000 条 4.83 ms。**上限就是几毫秒**。
- 唯一被它治到的：整表 DOM 重建（渲染层报告 3.3：600 行 705.6 ms、2000 行 2930.3 ms）。

也就是说：分页能拿到的收益，**P1 已经用"零交互回归"的方式拿到了一大部分**（P1 之后 600 行
一次性挂载的底色仍在，但"每次交互额外重排整表"已消除）。而它治不到的那几项，量级是
**一次保存 0.07～0.94 秒的磁盘写 + 0.04～0.85 秒的广播落地**，不是几毫秒。这就是"分页不是最优解"的准确含义——
不是它没用，是它**贵在自己不治病的那一半、省已经不太贵的那一半**。

### 6.1 「比 2 万条更大」的天花板问题（如果用户真要的是这个）

实测 479 B/条 + 10 MB 配额 ⇒ 单一 `account_passwords` 键在 5000 条时已占 2.4 MB，加上回收站、
历史（每条改动都存快照，`passwordHistory` 与主库同量级）、身份库，**约 2 万条是量级估计而非精确值**，
需要一次真实的"逼近配额"实验定位失败点（第十节列为未验证项）。届时只有两条路：

- **E1 分片**（把整库拆成 `aph_pwd_<id>` 多键或按 500 条分块）：绕过单值/单次写入的体积，
  写放大从 O(N) 降到 O(1)（4.2 实测 150×），但**总配额不变**——运行时读到的
  `chrome.storage.local.QUOTA_BYTES = 10,485,760` 是**总量口径**（多键不会各自拿到 10 MB），
  分片解决不了"存不下"，只解决"写太慢"。同时引入跨键一致性（现在靠**单键原子写**保证，
  `moveToTrash:87-90` 与 rekey 的 `:154` 多键单 set 都依赖这个性质；**键数上限与部分失败语义已于 09-25 实测：100/1000/2000/5000 键全部一次落地、无静默截断**，见设计稿 §5.3 M-1）。
- **E2 申请 `unlimitedStorage`**：直接抬配额。代价是权限清单变大（最小权限原则、
  `agents.md` 要求说明必要性并同步隐私/发布文档；CWS 对 `unlimitedStorage` 有额外审查）。
  对一个本地密码管理器来说"允许存多少自己的密文"技术上站得住，但**这条应该由用户决定，不是顺手加**。

### P1 扇出削峰（需要 1 次技术决策，不动格式、不动交互）

让一次变更携带"改了哪条/改了什么"，使 SW 与两个前端不再各自全量解密。可选实现：
`storage.local.set` 之后额外写一个轻量"变更票据"键（仅 id + 类别，不含明文字段），
或把 SW 的 `invalidate + warm` 改成"从已有缓存就地替换该条 + 重加密快照"。
**收益量级**：拿掉 3.2 表口径的 100～732 ms × 最多 2 路（SW/options 重复那两遍）。
**它拿不掉的**：4.2 的 `onChanged` 投递延迟（43～852 ms）——Chrome 的变更事件载荷就是整包
`newValue`，只要存储还是单键，结构化克隆与序列化就照付。
**风险点**：票据丢失或过期时必须能退回"全量重载"（正确性优先）。这条我先给设计，不直接实现。

### P2 写结构改造（**必须用户点头**；E1 与 C1/C2 不是同一件事，可单选也可组合）

4.2 取数后，这一档的**内部排序变了**：E1 治的是当前最大的单项成本，C1/C2 治的是零头。
但"数字更漂亮"不等于"风险更低"——E1 是三个选项里唯一同时触及**数据格式 + 迁移 + 一致性**的，

`chrome.storage.onChanged` 的 `changes` 只包含**被改的那个键**，各上下文因此拿得到"哪一条变了"的明文边界，
可以就地补 1 条而不是重解 5N 条——**这正是 P1「变更票据」想要的性质**。
所以若决定做 E1，P1 可以省掉（见第八节第 5 条）；反之，只做 P1 拿不到写侧那 0.07～0.94 秒的收益。

## 十、未验证项与风险（交付时如实声明）
